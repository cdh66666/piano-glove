## 1. 网页操控点一下就断联

**根因（两处，都在链路上不是"玄学"）：**

1. `host/bridge.py` 的串口读线程只要 `ser.read()` 抛一次异常，立刻 `_drop()` 把
   `connected` 置 False。CP210x 在 USB 抖动、系统省电、对端刚复位时都会抛一次然后自己恢复，
   于是"点一下"就掉线，接着桥在 2 秒后自己重连，日志里出现 `<<桥>> 自动连接 COM9`。
2. 掉线之后页面**没有任何恢复路径**：`startPolling()` 里 `if(!T.connected) return;`
   直接返回，`startBridgeWatch()` 一旦 `detectBridge()` 问不到桥就 `clearInterval` 永久放弃。
   结果是界面还写着"已连接"，点什么都像石沉大海，只能手动刷新页面。

3. 还有一条更隐蔽的：`host/delivery-shell.js` 的 `refresh()` 用
   `Promise.all([/api/status, /api/firmware])` 取状态。固件接口是"可选件"，可只要它
   4xx/5xx/超时一次，整个 `Promise.all` 就抛错 —— **已经拿到的串口状态一起被丢掉**，
   界面显示"读取状态失败"，`syncIdentity()` 和 `autoReconnect()` 全都不执行。
   用户看到的同样是"点一下就断联"，真实原因只是固件服务那一刻没应答。
4. `bridge.py` 的 `/api/connect` 对**空 body** 的处理是错的：页面有两处用
   `bridgePost("/api/connect", {})` 表示"不指定，你自己挑"，桥却把空 body 兜底成启动参数
   `--url` 的值，再拿它去 `rank_ports()` 里比对。`--url` 是 `socket://…`（联调）
   或已经拔掉的旧口名时必然对不上，于是回 **400「这个串口不是 USB 主控」**。
   用户看到的是"连不上、容易断"，实际线插着、口也好着。

**改法：**

- 读线程连续 5 次异常（间隔 120ms）才判定掉线；读到数据即清零计数。
- 页面新增 `bridgeRecover()`：轮询发现没连上（或 `STATUS_ALL` 一条 SLOT 都没回来）就自愈——
  问一次 `/api/status`，桥说已经连上就重新接管。绝不主动发 `/api/disconnect`。
- `startBridgeWatch()` 不再自尽：问不到桥只提示一次，继续每 1.5 秒巡视，桥回来了自动接管。
- `refreshSlots()` 改成返回布尔值，区分"6 个都离线"和"主控根本没回话"。
- `delivery-shell.refresh()` 里固件接口单独降级（`.catch(() => null)`），它挂了只影响
  烧录按钮的可用性，不影响串口状态、身份识别和自动重连。
- `/api/connect` 区分"调用方点名了端口"和"没点名"：点名了且不在候选里才回 400
  （这是有用提示），没点名就走 `autoconnect_once()`，不再拿 `--url` 当"点名"。

**验证：** 只读命令（INFO / STATUS_ALL / CAL STATUS）连续跑、`/api/status` 每 100ms 采样，
全程 `connected=True` 未抖。浏览器端到端 219 项**全过**（含"反复切换页面无异常"
和"桥这一段没有 JS 报错"两条，正是上面第 3、4 条修掉的）。
`tests/bridge_check.py` 用基线版本做过对照：同样的 4 项环境相关失败之外，
基线还会因空 body 回 400，本版不回。
**拔线/抖线场景没有实测**（需要你在现场拔一次线）。

## 2. 舵机编号：逻辑、文案、断点续编

**根因：**

- 编好号的 6 个舵机（ID 1~6）一起插着去点「检测当前舵机」，被判定成"总线上有 6 个舵机"，
  提示写的是**"多个同 ID 的舵机会互相抢答"** —— 纯属误报，它们的 ID 根本不同。
  同时流程被置成 `need-unplug`，「确认设为 N 号」永久灰掉，这就是你遇到的"卡住"。
- 进度只存在内存 `S.wizard` 里。刷新页面 / 断一次线 → 从 1 号重来。
- 总线空的时候提示是 **「总线是空的 ✔」**，一个绿色对勾。空总线不是成功，是"什么都没读到"。

**改法：**

- 新增判定：ID 恰好是 1~6 → 直接说"6 个舵机都在，编号已经是 1~6，不用再编了"，
  流程置 `done`，不再要求你拔舵机。
- 多舵机但 ID 不同 → 文案改为"总线上现在有 N 个舵机（1、2、3…）"，只有真·同 ID 才提"抢答"。
- 空总线 → 改成"没有读到任何舵机"，并列出三条排查（动力电源 / 插头到底 / 自检等 2 秒）。
- 编号进度存 `localStorage`（`pg.wizard.v2`，只接受从 1 开始的连续前缀，脏数据宁可丢），
  刷新/断线后显示"接着上次的进度：已经编好 1、2、3 号，下一个是 4 号"。
  「重新开始编号」会清掉存档。

**验证：** 实机（COM9，6 个舵机在线）点「检测当前舵机」→ 提示正确；
写入存档 → 刷新 → 恢复"接着上次进度"。已复验。

> ⚠️ **11-09 更正：这一节修错了对象。**

**根因：** 三个按钮都会"永久置灰"，没有任何恢复路径：

| 按钮 | 卡死原因 |
|---|---|
| 保存校准结果 | 只在采样定时器正常跑到结尾时才启用；中止/刷新/`CAL AUTO START` 报错后永远灰着 |
| 开始校准 | 从不 disabled，连点会并起多个定时器；某一个收尾时把进度按到 100% |
| 各手指「按一下」 | 中途抛错时停在"按下…"且 disabled，再也点不动 |

- `btnCalStart`：加 `calTimer` 硬闸防连点，`finally` 恢复按钮，定时器内 try/catch，
  出错停表并提示"可以点「开始校准」重来"。
- `btnCalCancel`：清定时器 + `refreshCal()`，让板子里已可用的数据能把保存按钮点亮。
- `refreshCal`：板子里有 min/max 但 `valid=0` 时，明确说"这套数据没通过校验，存不进去，
  请重新采一次"，而不是让按钮默默灰着（你机器现在就是 `valid=0` 这个状态）。
- 「按一下」：`try/finally` 恢复。

**验证：** 实机复验 `保存=灰 / 开始校准=可点`，提示文案正确。**完整采样→保存→使能→
按一下的动作链没有在实机上跑**（要动舵机，等你确认再跑）。

## 4. 固件集成进软件，不现场编译

原来：`host/firmware_flash.py` 现场调 PlatformIO 编译（`available()` 要求
`~/.platformio` 里的 pio / esptool / 源码齐全），客户机没工具链就整个烧录按钮是灰的；
另外客户面还有个「固件升级」外置文件夹（见第 5 条）。

现在：

- 新增 `tools/bundle_firmware.py`：把 `firmware/.pio/build/esp32dev` 的
  bootloader / partitions / firmware 加框架里的 boot_app0 冻结到
  `host/assets/firmware/`，并生成带 SHA-256 的 `manifest.json`。
  打包前会校验分区表必须是 `nvs=0x9000/0x5000`、`app0=0x10000/0x140000`，
  镜像碰不到校准区才允许打包。
- 冻结版本：**2.2.5-r29.8**（与手套当前 `ver=2.2.5-r29.8` 一致），写入区间固定
  `0x1000 / 0x8000 / 0xe000 / 0x10000`。
- `firmware_flash.build()` 改成"交出内置镜像"，不再编译；`available()` 只看镜像是否完好。
- 烧录器：把 **esptool 打进 EXE**，`desktop_runtime.py` 新增 `--esptool` 透传 ——
  冻结后的程序自己就是能跑 esptool 的解释器。客户机不需要 Python、不需要 PlatformIO。
- 调试台「主控固件」卡片去掉「仅编译」，只留「刷新 / 烧录主控」，并显示
  "内置版本 2.2.5-r29.8 · 已打包，无需编译"。
- 安全逻辑原样保留：烧前 `DISARM / RATE STOP / SAFE`、核对 CP210x 身份与 MAC、
  拒绝 ESP32-S3、`write_flash` 后 `verify_flash`、再开串口回读 `INFO` 校验版本与
  `armed=0`、不清空 NVS、失败不自动重连。

**验证：** `read_image()` 四项 SHA 校验通过；`pytest tests/test_firmware_flash.py`
13 项全过（含拒绝 S3、写入未验证、armed=1 拒绝）。

### 4.1 二次修复：打好的包里固件是「不可用」的（2026-11-08 深夜，你截图后才发现）

你在软件里点「固件版本」，弹窗写的是**「程序里的固件镜像不可用：重新解压一份完整的
钢琴手套软件再试」**，按钮点不动。也就是说第 4 条上一版**实际没生效**，只有界面文案换了。

根因在打包脚本，两处旧设计叠在一起：

1. `tools/build_customer_runtime.py` 的 `local_imports()` 里有一句
   `(HOST / (item + '.py')).is_file() and item != 'firmware_flash'` ——
   **故意把 `firmware_flash.py` 排除**在收集之外；
2. 紧接着 `prepare()` 无条件把这个模块**覆盖成禁用桩**：
   `available=False`、`version='2.2.4'`、`start()` 直接抛
   "测试版不提供固件源码构建"。

结果：我改的 `host/firmware_flash.py`（能读内置镜像那份）根本没进包，
进包的是那个恒返回不可用的桩，而 JS 侧文案是新的 ——
**界面说新话、后端跑旧桩**，正好是你截图那个样子。

为什么自检没拦住：`--self-test` 当时只查 39 个网页资源，不碰固件。

现在：

- 删掉 `item != 'firmware_flash'` 的排除，模块正常进包；
- 删掉整段桩文件写入，改成"镜像清单不存在就报错停止打包"；
- `customer_runtime.self_test()` 增加三项：`firmware_image_version`、
  `firmware_images`、`firmware_esptool`，镜像读不出来就直接让自检失败。

**验证：** 开发环境自检输出 `firmware_image_version=2.2.5-r29.8`、
`firmware_images=4`、`firmware_esptool=true`；打包后的 EXE 自检同样带这三项，
`available` 不再恒为 false。

> 这一条给我自己的教训：自检只覆盖"文件在不在"，没覆盖"功能能不能用"，
> 于是功能坏了也能打出一份全绿的报告。热修之后的情况必须实机点一遍才算数。

> （注释里写着"许可要求单独分发"），改成内置之后，主程序里就带了 GPL 组件。
> 对内自用/赠送客户一般没人管，但如果你要公开发布，得按 GPL 提供对应源码或改回外置升级器。

## 8. 「再调一遍」点了没用：第二次，真正的根因（11-09 深夜）

你截图那一刻：手套连着（COM9 已连接），6 台已编号，6 张手指卡片都是「0/1」，
点左下「再调一遍」——**界面一个像素都不动**。

### 8.1 为什么第 3 节没修好

客户版「调手套」页 = `web_piano_glove.html?simple=1` + `body.native-app`，
由 `desktop-debug.js` 改造成客户话术，校准逻辑全在 `delivery-demo.js`。
主按钮是 **`demoCalStart`**；第 3 节修的是调试台的 **`btnCalStart`**。两套按钮，两套状态机，
**没有任何共用代码**。所以第 3 节改完，客户版该坏还是坏。

### 8.2 三个叠在一起的问题

| # | 位置 | 问题 |
|---|---|---|
| 1 | `delivery-demo.js` 的 `demoCalStart.onclick` | `restartPending` 这把"防重入锁"把**整轮校准**（可能几分钟）都盖住了，而且 `await wizardRun` 等的是可能永不完结的 promise。只要上一轮卡住，点一次就永久卡在锁里，之后每次点击都在 `if(restartPending)return;` **静默退出** |
| 2 | 同上 | 锁内 `await wizardRun` 没有任何超时。串口桥在断联时可能一直不回，于是按钮从此变成砖头，只能重启软件 |
| 3 | `runCalibration()` 开头 | 忙时 `return`（静默）。调用方以为校准开始了，实际什么都没发生 |

还有一条体感问题：点击后先清状态、再发 `SAFE`，**这期间进度条一个字都不改**。
即使代码在跑，用户看到的也是"点了没用"。

### 8.3 改法

- `restartPending` 只盖住「停旧轮 + 清状态 + 起新轮」这一小段，**不再 await 整轮校准**
  （`wizardRun.catch(...)` 兜异常）。
- 等旧轮次改成 `Promise.race(旧轮次, 4 秒)`：4 秒还不退就 `wizardActive=false` 强制释放，
  并明说"上一轮没有正常结束，已强制停止"。
- `runCalibration()` 忙时**抛错**，不再静默 return。
- 点击瞬间就把进度写成「正在停止动作、解除使能…」；`SAFE` 加 5 秒上限，
  超时提示「主控 5 秒没有回应：检查 USB 线是否插好，再点「再调一遍」」。
- 启动前先检查 `deliveryDemoBusy()`，还占着就明确说"还有动作没停下，请点右上角「停止」"。

### 8.4 为什么 219 项全是绿的却没抓到

因为 `host/tests/e2e.js` **只加载调试台**（`?sim=1`），从头到尾没有 `simple=1`、
没有 `body.native-app`、没有 `delivery-demo.js` / `desktop-debug.js` 的任何一条路径。
客户版根本没有被自动化覆盖过。这是我上一轮说"测试全过"时没说清的部分，也是这次要补的洞。

新增 `host/tests/e2e-customer.js`（Playwright，无硬件）：

- 复刻 native 渲染的关键条件（`body.native-app` + `NativeApp` 垫片），加载客户版调手套页；
- 检查外壳：标题「调手套」、返回按钮、6 张手指卡、`⓪ 舵机编号` 排第一、曲目标签隐藏；
- **每次点击都必须有看得见的反应**（进度条 MutationObserver 计数 + DOM 指纹），
  空点 = 失败；
- **死锁回归**：把 `PianoDeliveryHooks.send` 换成永不 resolve 的 promise，
  制造"上一轮卡住"，然后连点三次——每次都必须在 1 秒内有反馈、4 秒内自救，
  且按钮不会变成砖头。

结果：**20 项全过**（改前该文件里 3 项直接红）。

> 这条测试的价值不在"又多了 20 个勾"，在于它证明了**客户版和调试台是两条路**，
> 以后改任何客户面按钮，都得在这里有对应断言。
