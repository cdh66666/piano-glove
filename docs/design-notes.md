| 2026-09-18 | 串口 RX 环形缓冲从默认 256 B 放大到 **4 KB**（`setRxBufferSize` 必须在 `begin` 前调用） | 256 B 在 115200 下只有 22 ms 余量，上位机一次连发 60 条约 1.1 KB 会溢出丢字节，表现为「发 60 条回 45 条」 |
| 2026-09-18 | **「试动作」点下去只锁电机不动 —— 根因是板子跑的是 v2.0.1 旧固件**，修好的 2.1.0 从未烧进去 | 实测 `INFO` 回 `ver=2.0.1`、`BUSINFO` 无回复。**结论：改完固件必须真烧录并回读 `INFO ver=` 复核**，「本地编译通过」不等于「板子上是这版」 |
| 2026-09-18 | `sendRecv()` 组包缓冲 `pkt[32]` → **`pkt[80]`**，并统一所有接收缓冲为 `RESP_BUF = 96` | `SYNC_WRITE` 一次写 6 根要 `2 + 7*6 + 6 = 50` 字节，`pkt[32]` 从第 4 根起写穿栈 → `Stack smashing protect failure!` 直接复位。RATE 一启动就崩就是这个 |
| 2026-09-18 | **`SETID` 拆成双语义**：`SETID <old> <new> CONFIRM` = 修号（`remapId`）；`SETID <old> <new> CONFIRM <slot>` = 编号向导（`setMap`，只认这一块） | 出厂新舵机 id 全是 1，编号向导第 2 轮发 `SETID 1 2` 按「修号」走会把第 1 轮已填好的槽位 0 一起改成 2，6 轮跑完得到 `[2,2,3,4,5,6]` —— 1 号舵机永远不动，界面却显示「编号完成」 |
| 2026-09-18 | 新增 **`RATE <slots> <speed> <acc> <depth%> [cycles]`** 板载测速命令，一次完整行程 = **最小 → 最大 → 最小**，结束打 `RATE_DONE` | 用户要「最小最大最小这样一个完整的算一次」。行程由板子自己跑，才量得到**真实机械频率**而不是命令频率 |
| 2026-09-18 | 测速**必须等舵机到位再发下一半程**，不等就是在量「我发包有多快」 | 早先版本不等到位，量出的是命令频率，与体感无关 |
| 2026-09-18 | 调试台加 **4C 测速卡片**，支持单独测某根 / 某几根 / 全部（掩码 `0x3F`），行程与速度都可调 | 直击用户诉求「可以单独测某根 某几根或者全部一起测试速度」 |
| 2026-09-18 | **模拟固件必须忠实实现固件语义**，尤其 `reset()` 不得清掉 `onAsync`、不得重置档位与校准 | 踩过两次：① `reset()` 清 `onAsync` → `RATE_DONE` 永远发不出，e2e 6 项 FAIL；② 「重置向导」顺带恢复出厂 → 档位掉回 `SC09`（量程 1023），模拟算出 11.6 Hz 而实机只有 5.0 Hz，**偏差 4 倍**。模拟一套、实机另一套，两类 bug 都测不出来 |
| 2026-09-18 | 演奏样本自带《两只老虎》（`host/samples/two-tigers.mid`，362 B / 32 音符），用于验证指法 | MIDI 生成脚本 `host/tests/make_two_tigers.py`；`check_midi.py` 做结构校验 |
| 2026-09-18 | **静止位必须落在「松开端」，不是量程中点**；抽出 `pressEnd()` / `releaseEnd()` 两个概念 | 用户原话「**怎么幅度这么小，要用我校准的最大幅度来啊**」。`autoFinish()` 原先把 `standby` 设为 `(min+max)/2`，而 `pressPos(s,100) = 按下端`，于是只从**中点**走 —— 按压幅度只剩校准行程的**一半**。`dir` 表示「按下去往哪边走」，不是「哪边数值大」 |
| 2026-09-18 | 新增 `snapStandby()`：开机自动把**存量**校准里明显跑偏（离松开端 > 量程 1/4）的静止位对齐到松开端；另给 `CAL ALIGN` 手动触发 | **老校准不用重做**。只修明显跑偏的，避免动到手工校准里有意留的偏移。实机 6 槽全部修正到位 |
| 2026-09-18 | 新增 `CAL ALIGN` 命令 + 校准页「修正静止位」按钮 | 让用户能一键修存量数据，而不是被迫重做第 3 步采样 |
| 2026-09-18 | **`MOVE <id> <pos>` 加校准区间越界闸**：超出该槽位 `[min,max]` 一律拒收回 `ERR MOVE out_of_cal_range ... add_FORCE_to_override`，显式带 `FORCE` 才放行（`FORCE` 在任意参数位置都认） | 用户原话「**测动作会卡死，转到不该转到的地方卡住**」。`MOVE` 是唯一能直接指定**原始位置**的命令，最易撞限位 |
| 2026-09-18 | **界面不再硬编码任何原始位置**：4B「测动作往返」从 `MOVE 1 200` 改为 `PRESS`/`RELEASE` 往返 | 实机读回校准表证实：`200` 对 **6 块舵机全部**落在区间外（区间分别是 `[2006,2708] [516,1208] [3514,4018] [1075,1661] [2418,3233] [552,1392]`），谁都顶死 |
| 2026-09-18 | 演奏的按压深度不再按 MIDI 力度衰减，改为默认**100% 完整校准行程**；新增「按压幅度」滑块（默认 100%） | 「幅度小」在演奏环节同样成立：原 `d = Math.max(0.35, e.vel)`，力度 0.7 就只按 70%。e2e 深度条从「不足 100%」变成 `100% × 6` |
| 2026-09-18 | **模拟固件的校准采样改为双向**（原来从静止位单向朝按压方向走） | 单向采样时 `min` 恰好等于起点，于是「中点 == 起点」，**静止位的 bug 在模拟里完全看不出来**；真机是「伸直 ↔ 握拳」双向动作，起点在中间。这是本项目第 3 次踩「模拟一套、实机另一套」 |
| 2026-09-18 | 单测**同一文件必须串行改**，禁止对同一文件并行发多个 Edit | 本轮踩了两次：并行 Edit 互相覆盖，`snapStandby()` 里的 `save()`、`FW_VER` 的修改都丢过。丢 `FW_VER` 那次是「bin 里版本串还是旧的」才发现的 |
| 2026-09-18 | 新增诊断脚本 `host/tests/diag_cal.py`：逐槽列出 `min/standby/max/方向/行程/当前位置/偏差/valid`，并把「拿某个原始位置去 `MOVE` 会不会越界」算给你看 | 校准类问题**不许猜**。这个脚本一跑就读出真机事实，也是它先报出「旧硬编码 `MOVE 1 200` 对 6 槽全部越界」 |
| 2026-09-18 | `host/tests/e2e.js` 的 `check()` 加计数器，结尾由脚本**自己打印总项数** | 文档里曾同时流传「114 项」与「125 项」两个互相矛盾的数字，因为总数一直是人肉数出来的。脚本自报后文档数字才有唯一来源（当前 **98 项**） |
| 2026-09-18 | **用户实机复验通过**：试动作满幅度、不再撞限位、整曲演奏节奏正确 | 本轮两个 bug（撞限位 / 幅度小）的用户侧验收结论。据此关闭 M8 卡点与 M10；关键是 `snapStandby()` 让用户**免于重做校准**，没有把一个内部 bug 变成用户的返工 |
| 2026-09-18 | **演奏页加「音乐 ↔ 演奏动作」同轴卷帘**：上半张 = 曲子本身（音高 × 时间），下半张 = 6 根手指的动作轨，共用一根播放头；丢音画灰影 | 用户原话「**需要能把音乐和演奏动作结合显示**」。原来的演奏页只有动作、没有声音，也看不出「这个音是哪根手指按的」 |
| 2026-09-18 | 声音用 **Web Audio 现场合成**（三角波基频 + 一点二次谐波，快起 + 指数衰减），不用 `<audio>` 播音频文件 | ① 单文件零依赖，不能引外部音源；② 音符本来就是逐条事件产生的，直接由 `note` 算频率，**声音与动作同源同刻**，不会出现「音频和动作对不齐」这种最难查的错；③ 用户不用另外准备音频文件 |
| 2026-09-18 | 默认**只响手套真的按下去的音**，另给「连被丢掉的音也一起响」开关做对比 | 默认要保证「听到的 = 看到的 = 手套做的」三者一致；那个开关是给「完整曲子 vs 手套演奏差多少」用的 |
| 2026-09-18 | 卷帘静态层用**离屏 canvas 缓存**，每帧只 blit + 画播放头；跟随模式的窗口起点**吸附到 2 秒网格** | 每帧重画几百个矩形没必要；而跟随模式下窗口若连续移动，静态层会每帧都失效 —— 吸附到网格后只在跨格时重画 |

> **航道修正**：本仓库初建时曾按「传感器 → MIDI 输出的演奏型手套」规划 README，与交接资料不符，已按实际的**舵机驱动型**重写。
> 注意方向别搞混：手套是**被 MIDI 驱动去动手指**，不是把手指动作转成 MIDI。

## 3. 关键技术风险

**1. 实时驱动的吞吐瓶颈（首要风险）—— 2026-09-18 已实测，结论：必须改固件**

原始需求要求「按行程 80%、0~6 Hz 正弦往复」。当前固件**没有频率驱动命令**，只有 `MOVE <id> <pos> <speed> <acc> ARM` 这种一次性定位。

**实测数据**（`host/bench.py`，COM3 / `PIANO_GLOVE_1`，6 个舵机全不在线）：

| 项目 | 实测值 |
| --- | --- |
| 单条 `INFO` / `CAL STATUS` 首字节往返 | **约 62 ms** |
| 单条 `PING 1` 首字节往返 | 约 123 ms |
| 单条 `STATUS_ALL` 首字节往返 | 约 680 ms（要轮询整条总线） |
| 上位机侧写入 60 条命令 | 1.4 ms（≈ 44000 条/秒，**这一侧不是瓶颈**） |
| **固件受理速率（连发 60 条实测）** | **≈ 9.9 条/秒**（每条约 103 ms） |
| 压测后是否仍响应 | 是（63 ms 恢复），不崩、不丢包 |

**结论**：需求 72 条/秒（6 指 × 6 Hz × 按下+抬起），实测天花板 **9.9 条/秒，差 7.3 倍**。

- **(a) 上位机逼近 —— 走不通。** 108ms / 103ms 不是舵机响应慢，是固件**每条命令都有固定的受理窗口**。串口 8KB 缓冲能吞下突发，但固件吐回复的速度就是 ~10 条/秒。演奏页「不等回复」策略不会卡死，但节奏会一路往后拖，几分钟就偏出好几秒。
- **(b) 改固件 —— 唯一可行路径。** 新增按频率往复驱动的原生命令，让板子自己跑正弦，把定时交给板子。**但固件源码不在本机**，等于要重写并重刷。成本高，但这是唯一能满足 6 Hz 的路。
- 注意 62~123ms 是**乐观下限**：舵机还没在线，在线后 `PING` 还要等舵机回包，会更慢。

> 复跑：`python host/bench.py`（自动找板子）／调试台第 4B 页（图形界面）。

**2026-09-18 收尾：风险已解除。** 自研固件 `PIANO_GLOVE_2` 上线后，突发 60/60 ≈ **413 条/秒**、
稳态 60/60 ≈ **1421 条/秒**，比原厂 9.9 条/秒快两个数量级，72 条/秒的需求留了 5.7 倍余量（稳态口径 20 倍）。

真正的新瓶颈**不在通信，在机械**：舵机本身的往返时间才是天花板。实测（`speed=0` 最快档）：

| 配置 | 实测频率 |
| --- | --- |
| 单根，满行程 | **7.10 ~ 7.15 Hz**（单程 70 ms） |
| 4 根同步，满行程 | 5.05 Hz |
| 5 根同步，满行程 | **4.97 Hz**（单程 100.7 ms，`lost=0`） |
| 5 根同步，行程 80% | 5.87 Hz |
| 5 根同步，行程 **60%** | **7.18 Hz** ✓ |
| 5 根同步，行程 50% | 8.07 Hz |
| 5 根同步，行程 40% | 9.30 Hz |

拟合 `半程耗时 ≈ 22 ms + 行程计数 / 6.6`（22 ms 是固件与总线固定开销，与行程无关）。
**这张表和 [firmware/README.md](../firmware/README.md#实机速度基准飞特-sts3032--6speed0-最快档) 里的那张是同一份数据，
改一处必须同步另一处；重测命令见文末「复跑入口」。**

**结论**：用户「6 Hz，最不济 4 Hz」的指标 —— **满行程 4.97 Hz 已保底达标；行程压到 60% 即稳定过 6 Hz**。
同步根数越多越慢（同步写要等最慢那根），所以「6 指全开 + 满行程」是 5 Hz 档，需要 6 Hz 时靠减行程换。

**2. 固件源码缺失**

`PIANO_GLOVE_1` 是别人写的闭源固件（交接前的前置工作已逆向其协议）。风险 1 的实测已经把这条路堵死了 —— **改固件不再是「可选优化」，而是继续推进的前置条件**。首先要解决的是「源码在哪 / 要不要重写」。目前 `firmware/` 里只有说明，没有源码。

**3. 舵机编号流程极其容易做废**

6 个舵机出厂 ID 全是 1，同总线会互相抢答，`SETID` 可能同时命中多个。必须一次只接一个。`assign_log.txt` 里已记录一次失败：编号向导在第 2 轮反复报「总线上还有 [1] —— 请把它拔下来」，说明**流程对人工插拔时序敏感**，需要更明确的提示或自动判别。

**2026-09-18 又挖出第二个、更隐蔽的坑**：出厂新舵机 id 全是 1，第 2 轮插上来的那块**也是 1**。
此时发 `SETID 1 2`，若按「修号」语义走 `remapId(1, 2)`，就会把第 1 轮已经填好的槽位 0
（它记录的 id 也是 1）**一起**改成 2。6 轮跑完得到 `[2,2,3,4,5,6]`：

| 轮次 | 操作 | 期望映射 | 实际映射 |
| --- | --- | --- | --- |
| 1 | `SETID 1 2` slot=0 | `[2,-,-,-,-,-]` | `[2,-,-,-,-,-]` |
| 2 | `SETID 1 3` slot=1，remap 命中槽位 0 | `[2,3,-,-,-,-]` | `[3,3,-,-,-,-]` ✗ |
| … | … | … | … |
| 6 | 全部完成 | `[1..6]` 顺序打乱 | `[2,2,3,4,5,6]` ✗ |

后果是**槽位 0 和槽位 1 指向同一块舵机，1 号那块永远不动**，而界面一路显示「编号全部完成」。

修法（已落地，固件 v2.1.1）：
1. `SETID` 带 `slot` 参数时走 `setMap(slot, new)` —— **只认这一块，别的槽位一律不碰**；
2. `ENROLL` 状态机发现 `cur == 目标 id` 时也必须**补写映射**（原来直接 return，映射就丢了）；
3. 上位机编号流程在 `cur === target` 时补发 `MAP <slot> <id>`。

**回归防线**：`host/tests/e2e.js` 不再断言界面文案，而是直接读固件映射 ——
`STATUS_ALL` 解析出的槽位 id 序列必须等于 `1,2,3,4,5,6`。
做过变异测试：把修复退掉，模拟固件给出 `[2,2,3,4,5,6]`，该断言立刻变红（`失败 2 项 ✘`）。

**4. 多轴协同的一致性**

6 个舵机按压同一只手，如果各轴 `CAL` 的 standby/min/max 不一致，「同时按下」会变成参差不齐的错音。校准必须逐槽位验证。

**5. `SCAN` 漏报与 `PING` 慢**

`SCAN` 约 1/3 概率返回 `count=0`；`PING` 单次约 123 ms（舵机不在线时），遍历 10 个 ID 仍要 1.3 秒。导致任何「上线检测」都慢且不稳，上位机轮询建议 2~3 秒一次。

注：早先记录的「`PING` 单次 610 ms」是**含读取尾部静默超时的合计值**，2026-09-18 用首字节计时修正为 ~123 ms；但**固件受理速率仍是硬伤（见风险 1）**。

**2026-09-18 随固件重写解除**：自研固件把舵机侧超时窗口收到 20 ms，`SCAN` 不再出现 `count=0`；
后台在线状态轮询改成**轮转单槽 + 8 ms 超时**（原来一次刷 6 槽 × 20 ms = 120 ms，
会把这期间到达的所有命令往后推，演奏场景不允许这种周期性抖动）。实机 `SCAN` 稳定报 6 块。

**6. `ENROLL` 流程语义未摸清**

固件自带的舵机注册流程（`ENROLL START/STATUS/STOP/RESET`），其 `requirement` 字段提示了一个三段式流程（先 1→10，再以 ID1 作为 2~6 加入，再 10→1），但语义未验证。**用完记得 `ENROLL STOP`**，否则可能影响正常动作。

**2026-09-18 处置**：原厂那套三段式 `requirement` 语义**不沿用**，自研固件把 `ENROLL` 重写成
一个直白状态机 —— **必须检测到总线为空（只有本机）才允许插下一块**，插上后自动判定 id、
必要时改号、然后写映射，全程打 `ENROLL ASSIGNED id=N slot=M`，人只要照着提示插拔即可。
这条正是为了解决上面 `assign_log.txt` 里「反复刷『请把它拔下来』」的死循环。

**7. MIDI 演奏的实时性（新）**

一个音符要发 2 条命令（按下 + 松开）。实测样本曲目在 6 秒内有 85 个音符 → 峰值约 **58 条命令/秒**，平均 27 条/秒。

- 模拟模式下完全无压力，但模拟固件是**零延迟**的，不代表实机。
- ~~实机已实测：固件受理上限 ≈ 9.9 条/秒，峰值 58 条/秒根本发不完 —— 差 5.9 倍。~~
  **2026-09-18 已随固件重写解除**：自研固件稳态 ≈ 1421 条/秒，58 条/秒连 4% 都不到。
- 应对（已实现，保留）：播放引擎每帧最多补发 40 条命令，超出部分**直接跳过** —— 宁可丢音，也不让延迟累积把后面的节奏整体推歪。
  新固件下这个上限不会再被触发，但作为兜底留着。
- **新的真实瓶颈是机械而非通信**：一个音符要 2 条命令（按下 + 松开），而一次按压的物理行程耗时
  （满行程约 100 ms，见风险 1 速度表）**远大于**发命令的时间。所以演奏能多快，取决于
  「按住时长 + 抬起时间」而不是总线带宽 —— 这也正是为什么按住时长要夹在 55~200 ms（见 §1）。

**8. 6 个自由度 vs 钢琴的十几个音**

手套只有 6 个执行器，出现「同时需要 7 根手指」时必然丢音。当前策略是按空闲槽位贪心分配，实在没有空闲就丢。**对「感受节奏和速度」这个目标来说，保住时间轴比保住每个音更重要** —— 所以丢音是设计选择，不是 bug。

**9. 校准是按「槽位」存的，不是按舵机 ID 存的（已踩实机）**

`CAL` 记录的是**槽位 → min/standby/max 计数**，槽位背后是哪块舵机由 `MAP` 决定。
所以 **一旦动过 `MAP` / `SETID`，旧校准就作废**，必须重做第 3 步校准。

实机已踩到一次：**槽位 0 的校准数据实际是拿 2 号舵机采的**（当时映射还是 `[2,2,3,4,5,6]`）。
映射修成 `[1,2,3,4,5,6]` 后，槽位 0 指向 1 号舵机，而记录里的「静止位 782」
与 1 号舵机的实际位置 **2091** 差了 **1309 计数（≈115°）** —— 照这个校准去按，
会直接顶到机械限位。

- 处置：已用 `MAP 0 1` 修正映射。**槽位 0 的旧校准数据不需要重做** —— 真正的原因不是
  「校准采错舵机」，而是静止位取错了端点（`autoFinish()` 用了量程中点），
  固件 v2.1.2 的 `snapStandby()` 一开机就把静止位对齐到松开端（实机读回见文末表格）。
- 防线：`host/tests/bench_move.py` 内置安全闸 —— 校准值与当前位置差超过 **600 计数**
  就判定「这份校准不是这块舵机的」，**默认跳过该槽位不动**，要测必须显式加 `--force`。
  实测就是靠这个闸先发现异常的。

**10. `INST_WRITE` 的第一个参数必须是起始寄存器地址**

飞特 SCS/STS 的 `INST_WRITE`（指令码 3）参数列表的第一字节**不是数据，是寄存器地址**。
漏掉它会让舵机把数据当成地址，回包错误位非 0 —— **而错误位在第 5 字节，不是指令码**，
所以「舵机回包了」不等于「舵机照做了」。协议细节见
[`../firmware/README.md`](../firmware/README.md) 对应章节。
