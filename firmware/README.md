# firmware · 主控固件（自研 `PIANO_GLOVE_2`）

> **2026-09-18 起，本项目不再依赖别人的固件。** 这里就是源码。

板子跑的是本项目自研的 `PIANO_GLOVE_2`，替代原来那块闭源的 `PIANO_GLOVE_1`。
**文本协议逐命令兼容** —— `host/web_piano_glove.html` 和 `host/glove_fw.py` 一行都不用改。

---

## 为什么重写

原厂固件（别人写的、源码不在手上的那块）只有一个致命问题，但它卡死了整个上层需求：

| | 原厂 `PIANO_GLOVE_1` | 自研 `PIANO_GLOVE_2` |
| --- | --- | --- |
| 单条命令处理 | 固定约 **103 ms** | 收到回复立即返回，超时窗口 20 ms |
| **固件受理速率** | **9.9 条/秒**（实测） | 只受 1 Mbps 总线限制，理论上百条/秒 |
| 6 指 × 6 Hz 需要 | 72 条/秒 → **差 7.3 倍** | 满足 |
| 板载扫频（行程 % / 频率 / 时长） | ❌ 没有 | ✅ `SWEEP` |
| 舵机编号流程 | 状态语义含糊，实测会死循环 | ✅ `ENROLL` 状态机，总线清空才允许插下一个 |

那 103 ms 与舵机无关，是固件每条命令的固定等待窗口 —— 所以**上位机再怎么优化都没用**，
必须换固件。实测数据见 [`../host/bench.py`](../host/bench.py) 与
[`../docs/design-notes.md`](../docs/design-notes.md) 的风险 1。

## 源码结构

```
firmware/
├── platformio.ini        esp32dev / espressif32@6.4.0 / Arduino
└── src/
    ├── scs_bus.h/.cpp    飞特 SCS/STS 协议驱动（官方 Python SDK 的 C++ 移植）
    ├── glove.h/.cpp      槽位模型、校准表、按压/松开、扫频引擎、NVS 持久化
    └── main.cpp          命令分发 + ENROLL 状态机
```

### 协议实现要点（写代码时最容易错的地方）

- 包格式 `0xFF 0xFF ID LEN INSTR PARAM... CHECKSUM`，`LEN = 参数数 + 2`，总长 `LEN + 4`
- 校验和 `~(ID + LEN + INSTR + PARAM...) & 0xFF`
- **状态包第 5 字节是错误码，不是指令** —— 请求包的 `INSTR` 位在回包里成了 `ERR` 位，
  这是区分「自己发的回显」和「舵机的回复」的唯一依据之一
- 反馈一次读 **56~70 共 15 字节**（位置/速度/负载/电压/温度/运动中/电流），省 7 次往返
- 改舵机 ID 前要先写 `LOCK=0` 解锁 EEPROM，改完再上锁；
  **写入后必须等约 300 ms 再 `PING` 新 ID 复核** —— 舵机应用新 ID 需要时间

### 写给「试动作时舵机纹丝不动」：`INST_WRITE` 的第一个参数必须是寄存器地址

这是用户实机反馈的头号问题：第 4 步「试一下动作」点下去，**只有 TORQUE 把电机锁死了，
按下去一点都不动**，日志里还是 `OK`。

根因在 `moveTo()`：

```cpp
// ✗ 错：INST_WRITE 的参数里，第一个字节必须是**起始寄存器地址**
uint8_t p[8];
p[0] = acc;                 // ← 舵机把 30（ACC 的默认值）当成了「寄存器地址 30」
p[1] = pos & 0xFF;
...                          // 于是收到一条"往寄存器 30 写 6 字节"的指令，
                             // 越界/受保护 → 舵机回一个**错误包**
```

而 `sendRecv()` 当时只判断「有没有收到校验正确的回包」，**没看错误位**，
于是把舵机拒收报成了成功。TORQUE 之所以看起来"生效"，是因为它走的是 `writeRegs()`
（那个实现里有 `p[0] = addr`，是对的）—— 所以电机锁了、手指不动。

修法是两件事一起做：

1. `p[0] = REG_ACC;` 并把参数长度从 7 改成 8；
2. **加错误位检查**（见下面「错误位不再被吞掉」），
   这类 bug 以后第一眼就能看见，而不是伪装成 `OK`。

实机验证结果：6 根舵机发指令前后各读一次位置，位移 271~592 计数全部到位，`servo_err` 不涨。

### 串口接收缓冲必须放大（v2.0.1 修的坑）

Arduino-ESP32 的 `HardwareSerial` RX 环形缓冲**默认只有 256 字节**。
115200 8N1 下这只相当于 22 ms 的余量 —— 而上位机在演奏场景会一次连发几十条命令，
只要主循环在 `glove::tick()` 里停 8 ms 去读总线，环形缓冲就溢出、字节被丢，
现象是「发 60 条只回 45 条」并且回复内容被截断。

修法是 `Serial.setRxBufferSize(4096)`，且**必须在 `Serial.begin()` 之前调用**才生效
（`_rxBufferSize` 是 `HardwareSerial` 的 protected 成员，没有公开 getter，
所以 `READY BUS ... uart_rx_buf=` 里打印的是一个编译期常量 `UART_RX_BUF`）。

另外 `loop()` 里加了一个行缓冲溢出保护：单行超过 255 字节时丢弃整行并计数，
计数从 `BUSINFO` 的 `rx_drop=` 读出 —— 若这个数在涨，说明上位机发得太快或发坏了。

`host/tests/verify_firmware.py` 现在区分两种压测：
`burst()` 一次性猛灌（考突发吸收）、`burst_paced()` 每 2 ms 一条（考稳态处理）。
两个数字一起看才能判断丢包发生在链路还是在固件。

### 回显处理（很容易踩）

端口探测时会向不存在的 ID 发一条 `PING`，数收到几个字节：收到等于自己发包长度的字节数，
说明板上 TX/RX 是并联的（半双工常见做法），后续每发一包都要先吃掉这段回显。
`BUSINFO` 里的 `echo=` / `echo_bytes=` 就是这件事，`ECHO 0|1` 可以手动覆盖。

### `sendRecv` 的组包缓冲曾经只有 32 字节（v2.1.1 修的坑，会直接复位）

`sendRecv()` 内部用一块 `pkt[80]` 组装要发出去的包，长度是 `参数数 + 6`。
它曾经是 `pkt[32]`，而 **`SYNC_WRITE` 每根舵机要写 7 字节 + 2 字节头**：

| 同步写的舵机数 | 参数长度 | 需要 `pkt` |
| --- | --- | --- |
| 1 | 9 | 15 |
| 3 | 23 | 29 |
| **4** | 30 | **36** ← 越界 |
| 6 | 44 | 50 ← 越界 |

第 4 根起就写穿栈，第 6 根必然踩碎栈保护金丝雀，现象是串口直接吐
`Stack smashing protect failure!` 然后 `Rebooting...`，**RATE 一启动板子就重启**。

这个坑藏得很深：单根 `MOVE` 只写 8 字节参数、`writeRegs` 最多 24 字节、
`syncReadPos` 最多 18 字节 —— 全都在 32 以内，所以日常单指测试完全看不出来，
只有「多根一起同步写」才会炸。第一次 6 根一起跑 `RATE` 才暴露。

同类问题还有一处：`readPacket()` 会把舵机回包原样 `memcpy` 到调用者的缓冲里，
长度由回包里的 `LEN` 字段决定（最大 96）。所以本文件里**所有接收缓冲统一用
`RESP_BUF`(=96)**，保证「舵机回了个超长包」也不会写穿栈。

### 编号流程曾经把已编好的槽位改掉（v2.1.1 修的坑）

`SETID` 和 `ENROLL` 两条路上都用错了函数：

```cpp
// ✗ 错：remapId 的语义是「某块舵机改了号，把指向它的槽位都跟着改」，
//       用在编号流程里会连**已经编好的槽位**一起带走
glove::remapId(cur, target);
```

编号向导每轮插上来的都是**出厂新舵机，出厂号全是 1**，于是：

| 轮次 | 插上的舵机 | 目标 | 错误行为 | 槽位表 |
| --- | --- | --- | --- | --- |
| 1 | id=1 | 1 | 「正好是目标号」，不改号 → **映射根本没写** | `[1,2,3,4,5,6]` |
| 2 | id=1 | 2 | `remapId(1,2)` 把**槽位0 也改成 2** | `[2,2,3,4,5,6]` ✗ |
| 3~6 | id=1 | 3~6 | `remapId(1,N)` 找不到 id=1，无副作用 | `[2,2,3,4,5,6]` |

结果：槽位 0 和槽位 1 指向同一块舵机，**1 号舵机永远不动**，
而向导界面照样显示「✔ 6 个舵机全部编号完成」。实机复现就是这个值 `[2,2,3,4,5,6]`。

修法两条：
1. `SETID` 增加可选槽位参数 —— `SETID <old> <new> CONFIRM [slot]`。
   给 `slot` 走「编号向导」语义（`setMap(slot,new)`，只动这一个槽位）；
   不给则保持「修号」语义（`remapId`）。`ENROLL` 内部也改用 `setMap`。
2. 上位机无论改不改号，都要把映射显式写下去（不改号时补一条 `MAP`）。

回归由 `host/tests/e2e.js` 的「编号后槽位映射 = 1..6」守住 ——
它不看界面文案，直接读固件的 `STATUS_ALL`。这条断言做过变异测试：
把修复退掉就会红，值正好是 `[2,2,3,4,5,6]`。

### 静止位曾经被设成「量程中点」，导致按压只用半个行程（v2.1.2 修的坑）

用户的反馈是「**怎么幅度这么小，要用我校准的最大幅度来啊**」。

踩坑的位置是 `glove.cpp` 的 `autoFinish()`：

```cpp
g_slot[s].standby = (uint16_t)(((uint32_t)g_autoMin[s] + g_autoMax[s]) / 2);  // ✗ 中点
```

第 3 步「跟着提示活动手指」采出来的是 **手指完全伸直 ↔ 压到底** 的整个量程。
`standby` 却取了量程中点，而按压力公式是

```
pressPos(s, 100) = standby + (按下端 - standby) * 100/100 = 按下端
```

于是**从中点走到按下端 —— 只用了校准行程的一半**。

先把两个概念分开（`pressEnd` / `releaseEnd`）：

```cpp
// dir 描述的是**按下去往哪边走**，不是"哪边数值大"：
//   DIR_PRESS_MAX -> 按下端 = hi，松开端 = lo
//   DIR_PRESS_MIN -> 按下端 = lo，松开端 = hi
//
// 静止位必须落在**松开端**：按压才是从"手指完全松开"一路走到"完全按下"，
// 也就是校准出的整个量程。
uint16_t pressEnd(int s)   { return (sl.dir == DIR_PRESS_MAX) ? sl.hi : sl.lo; }
uint16_t releaseEnd(int s) { return (sl.dir == DIR_PRESS_MAX) ? sl.lo : sl.hi; }
```

修法三条：

1. `autoFinish()` 改成 `standby = releaseEnd(s)`；`setDir()` 换方向时静止位跟着挪到新的松开端。
2. 新增 `snapStandby()`：把**存量**校准里"明显跑偏"（离松开端超过量程 1/4）的静止位
   对齐到松开端，`begin()` 开机自动跑一次 —— **老校准不用重做**。
   只修明显跑偏的，避免动到手工校准里有意留的偏移。
3. `pressPos()` 加区间夹紧，坏数据算到区间外也不会打穿限位。

另外给 `MOVE` 加了越界闸（见下），并新增 `CAL ALIGN` 手动触发第 2 条。

**这一坑为什么模拟模式看不出来**：模拟固件的采样原来是**从静止位单向**朝按压方向走的，
`min` 恰好等于起点，于是「中点 == 起点」，bug 在模拟里完全消失。
真机上用户做的是「伸直 ↔ 握拳」**双向**动作，起点在中间，中点 ≈ 起点，实机就只剩半个行程。
已把模拟改成忠实实现（双向采样），并在 `e2e.js` 加了两条断言守住：

```
PASS  静止位落在松开端（不是量程中点）   [0:2184→2184 1:1878→1878 ... 5:1761→1761]
PASS  按压行程 ≈ 整个校准量程           [0:277/277 1:345/345 ... 5:556/556]
```

### `MOVE` 会一路顶到机械限位（v2.1.2 修的坑）

用户的反馈是「**测动作会卡死，转到不该转到的地方卡住**」。

界面第 4B 页原来的「测动作往返」硬编码 `MOVE 1 200` —— `MOVE` 收的是**原始寄存器位置**，
而 200 对**每一块**舵机都落在校准区间之外：

| 槽位 | id | 校准区间 | `MOVE 1 200` |
| --- | --- | --- | --- |
| 1 | 1 | `[2006, 2708]` | 区间外 → 顶死 |
| 2 | 2 | `[516, 1208]` | 区间外 → 顶死 |
| 3 | 3 | `[3514, 4018]` | 区间外 → 顶死 |
| 4 | 4 | `[1075, 1661]` | 区间外 → 顶死 |
| 5 | 5 | `[2418, 3233]` | 区间外 → 顶死 |
| 6 | 6 | `[552, 1392]` | 区间外 → 顶死 |

`MOVE` 是唯一能直接指定原始位置的命令，也是最容易撞限位的一条。两条修法：

1. **固件加越界闸**：目标落在该槽位校准区间外就拒收，回
   `ERR MOVE out_of_cal_range id=.. pos=.. allowed=lo..hi add_FORCE_to_override`。
   确实要越界时显式加 `FORCE` 才放行（`FORCE` 在**任意位置**都认，不限于第 5 个参数之后）。
2. **界面不再发 `MOVE`**：「测动作往返」改为「按一下 ↔ 松开」往返
   （`PRESS <slot>` / `RELEASE <slot>`），走的是校准区间本身，天然不会越界。
   UI 从此不硬编码任何原始位置。

回归断言（同样做过变异测试）：

```
PASS  MOVE 越界被拒绝（目标在区间外）  [id=1 pos=1407 区间=1907..2184 → ERR MOVE out_of_cal_range ...]
PASS  MOVE 区间内放行                  [OK MOVE id=1 pos=2046]
```

## 命令集

### 与原厂完全兼容（上位机无需改动）

`INFO` `PROFILE` `PING` `SCAN` `STATUS` `STATUS_ALL` `MAP` `SETDIR` `SETID`
`CAL (STATUS/CLEAR/CAPTURE/SAVE/AUTO START|STATUS|FINISH|CANCEL)`
`TORQUE` `ARM` `DISARM` `SAFE` `STANDBY CONFIRM` `PRESS` `RELEASE` `MOVE` `DEMO`
`AUTO` `ENROLL` `HELP`

回复格式逐字段对齐（含 `SLOT` / `CAL` / `CAL_AUTO` 行的字段顺序），
所以调试台和 CLI 的解析逻辑一个字都不用动。

### 自研新增

| 命令 | 作用 |
| --- | --- |
| **`SWEEP <slots> <freq_mhz> <depth%> <dur_ms> [speed] [acc]`** | 板载扫频。`slots`：`0`/`all`=全部，`1..6`=单个槽（1 起），`0x3F`=位掩码；`freq_mhz` 单位 0.001 Hz（`6000` = 6 Hz）；`depth%` 行程百分比（**原始需求是 80**）；`dur_ms` 持续时长。结束时自动松手并打印 `SWEEP_DONE` |
| `SWEEP STOP` | 中止扫频，回到 standby |
| `SWEEP` | 查看当前扫频状态 |
| **`RATE <slots> <speed> <acc> <depth%> [cycles]`** | **速度实测**。和 `SWEEP` 的区别：`SWEEP` 是按给定频率猛发目标位置（测「命令频率」），`RATE` 是**每个半程都等舵机真正到位才发下一半**（测「机械上真能跑多快」）。一次完整行程 = 最小→最大→最小；跑够 `cycles` 趟后打印 `RATE_DONE cycles=.. half_ms=.. full_ms=.. hz=.. slow_ms=.. lost=..`。`lost>0` 表示有半程等满 800 ms 都没到位（卡住或跟不上） |
| `RATE STOP` / `RATE` | 中止 / 查看进度（`active= done=/ half_ms= slow_ms= lost=`） |
| `BUSINFO` | 总线诊断：引脚、波特率、回显判定、收发计数、超时数、校验错数、**`servo_err=`（舵机错误位累计次数）** |
| `ECHO 0\|1` | 手动覆盖回显判定 |
| `PRESET <speed> <acc>` | 设置 `PRESS`/`RELEASE`/`DEMO` 的默认速度与加速度 |
| **`CAL ALIGN`** | 把各槽位的静止位对齐到「松开端」（修 v2.1.1 及更早自动校准留下的量程中点），**不用重做采样**。回 `OK CAL ALIGN fixed_mask=0x3F standby_moved_to_release_end`；`fixed_mask=0x00` 表示本来就正确。开机 `begin()` 也会自动跑一次 |

扫频用 **SYNC_WRITE 一帧同时更新所有参与槽位**，所以 6 指同时扫也不会因为逐个下发而错位。
`RATE` 的到位判定用 **SYNC_READ 一帧问、多舵机回**，省掉 6 次往返。

### 错误位不再被吞掉

飞特状态包的第 5 字节是**错误位**（不是指令码）。旧代码只判断「有没有收到校验正确的回包」，
于是**舵机拒收指令时也返回成功** —— 这正是「试动作时只有 TORQUE 锁住了电机、按下去纹丝不动」
却看不到任何报错的原因。现在：

- `scs::lastError()` 暴露最近一条状态包的错误位，`BUSINFO` 的 `servo_err=` 累计非零次数；
- `PRESS` / `RELEASE` / `MOVE` 遇到非零错误位一律回 `ERR ... servo_rejected ... err=N`。


### 行为上的差异（有意为之）

- `MOVE <id> <pos>` 的 `speed`/`acc`/`ARM` 变成**可选**。原厂会回 usage 错误
  （测出来的往返时间其实只是报错时间）。上位机的「响应速度实测」页原先只发 `MOVE 1 200`，
  但 `200` 对任何一块舵机都在校准区间之外、会顶死限位，**v2.1.2 起该页改走 `PRESS`/`RELEASE`**。
- `MOVE <id> <pos>` 新增**校准区间越界闸**：超出该槽位的 `[min,max]` 一律拒收
  （`ERR MOVE out_of_cal_range ... add_FORCE_to_override`），确需越界得显式带 `FORCE`。
  这是 v2.1.2 加的 —— 见上文「`MOVE` 会一路顶到机械限位」。
- `PROFILE SC09` 返回 `ERR`。原厂接受但在 SC09 档下舵机 ping 不通；本固件只有 STS 寄存器表，
  报错比假装接受更诚实。
- `DISARM` 会有回复（原厂无回复）。有回复总是更好调试。

1    拇指下压   2   516   1208    1208  min   692   864    344

6 槽 `valid=1`，`standby` 全部落在松开端（`dir=min` 时松开端 = `max`），
按压行程 = 完整量程；**每块舵机的当前位置都落在自己的校准区间内**。
（此前的「槽位 0 的静止位 782 vs 实际位置 2091」异常，在映射修正 + `snapStandby()` 后消失。）

### 实机速度基准（飞特 STS3032 × 6，`speed=0` 最快档）

| 配置 | 实测 |
| --- | --- |
| 单根，满行程 | **7.10 ~ 7.15 Hz**（单程 70 ms） |
| 4 根同步，满行程 | 5.05 Hz |
| 5 根同步，满行程 | **4.97 Hz**（单程 100.7 ms，`lost=0`） |
| 5 根同步，行程 80% | 5.87 Hz |
| 5 根同步，行程 **60%** | **7.18 Hz** |
| 5 根同步，行程 50% | 8.07 Hz |
| 5 根同步，行程 40% | 9.30 Hz |

结论：**满行程跑不到 6 Hz（4.97），把行程调到 60% 就轻松过 7 Hz。**
真弹琴手指本来也不用压到底，所以这个门槛不是问题。
单程耗时可以拟合成 `half_ms ≈ 22 + 行程 / 6.6`（22 ms 是通信往返 + 起停的固定开销），
调试台的「该调到多少行程」就是按这个反推的。

### 真机上必须注意的一个坑：校准是**按槽位**存的

`MAP` 改了槽位指向哪块舵机之后，**那个槽位的校准数据就作废了** ——
它记的是**上一块舵机**的行程，套到新舵机上可能把机构顶到限位。
实机上就踩到过：槽位 0 记录「静止位 782」，而实际那块舵机停在 2091（差 1309 计数 ≈ 115°）。

所以 `host/tests/bench_move.py` 内置了一条安全闸：**校准值和当前位置对不上的槽位默认不动**，
要在第 3 步重做校准（`--force` 可以强行测）。

### 上电后按这个顺序验证

```
BUSINFO                 # echo=1？→ TX/RX 并联正常；servo_err 应为 0
INFO                    # 应回 fw=PIANO_GLOVE_2 profile=STS3032 range=4095 ver=2.1.2
PING 1                  # 接上舵机后逐个数
STATUS_ALL              # 6 个槽位在线情况；核对每行 id= 是不是 1~6 一一对应
CAL STATUS              # 重点看 standby= 是不是等于 min/max 里的**松开端**（不是中点）
```

接上舵机后的完整实机验证一条命令搞定（需要 pyserial）：

```bash
python host/tests/bench_move.py COM3 --rate --rate-cycles 3 --rate-depth 60   # 验位移 + 测速
python host/tests/diag_cal.py                                                  # 读校准表 + 越界体检
```

`diag_cal.py` 会逐槽列出 `min / standby / max / 方向 / 行程 / 当前位置 / 偏差 / valid`，
并把「界面若拿某个原始位置去 `MOVE` 会不会越界」直接算给你看。
**方向对不上、或静止位不在松开端，就用它先诊断，别靠猜。**

## NVS 持久化

命名空间 `pianoglove`。键：`speed` / `acc` / `calib`，
每个槽位 `s{n}id` / `s{n}lo` / `s{n}st` / `s{n}hi` / `s{n}vd` / `s{n}d`。

`MAP` / `SETDIR` / `SETID` / `CAL SAVE` / `CAL CAPTURE` / `ENROLL` 会自动落盘，
断电重连后槽位映射和校准值都还在 —— 这是原厂固件做不到的便利。

烧录用的是 `pio run -t upload`（只写 bootloader / partitions / boot_app0 / app 四段），
**不会动 0x9000 起的 NVS 区**，所以重新烧固件不会丢校准。
