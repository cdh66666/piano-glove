# host · PC 侧上位机与调试工具

通过 USB 串口（CP2102，**115200 8N1**）与主控板上的 `PIANO_GLOVE_1` 固件通信。

> 协议细节见 [../docs/handoff-2026-09-17.md](../docs/handoff-2026-09-17.md#2-固件-piano_glove_1-命令协议核心)。

## 串口为什么不在页面里

页面想开串口只有 Web Serial（`navigator.serial`）。它要求：电脑版 Chrome/Edge + 安全上下文。
落到实际使用上就是：

- 侧边栏浏览器 / 内嵌 WebView / 微信内置浏览器 → **没有这个 API**，点「连接」永远没反应；
- 每次连接都要弹系统级的选口框 → 没法"自动选推荐口"；
- 双击 `.html` 走 `file://` → 直接没有。

所以 `bridge.py` 把串口搬到了 Python 侧。页面只跟 `127.0.0.1:8123` 说 HTTP，
**用什么浏览器都能用**，而且选口这件事完全不用用户操心。

### 桥的 HTTP API

| 接口 | 说明 |
| --- | --- |
| `GET /api/status` | 桥/串口状态 + 端口清单（含打分与理由）+ 推荐口 |
| `GET /api/lines?since=N&wait=S` | 长轮询拉异步行（`RATE_DONE` 这类"过一会儿才吐"的回复靠它） |
| `POST /api/scan` | 重扫串口 |
| `POST /api/connect` | `{}` = 自动挑推荐口；`{"port":"COM4"}` = 指定 |
| `POST /api/disconnect` | 断开，并**暂停**自动重连（否则前脚断开后脚又连回来） |
| `POST /api/send` | `{cmd,timeoutMs,quietMs,since}` → `{pre,lines,first,ms,seq}` |
| `POST /api/fire` | 只发不等（整曲演奏时用，不能被固件延迟卡住） |

`pre` 是「命令发出前就已经在缓冲里的行」（板子上电主动上报的 `BOOT` 之类），
单独还给页面，免得混进命令回复里。

`pre` 是「命令发出前就已经在缓冲里的行」（板子上电主动上报的 `BOOT` 之类），
单独还给页面，免得混进命令回复里。

安全上只 bind `127.0.0.1`，并校验 `Origin`：**别的网站发起的跨站请求一律 403** ——
不然随手打开的某个网页就能 POST `/api/fire` 去拧你的舵机。
放行的来源 = 本机（`127.0.0.1` / `localhost` / `::1`）+ `null`（`file://` 双击打开的页面）。

### 页面怎么找到桥（2026-09-20 修）

页面**不假设桥就开在自己的来源上**。它会按候选清单挨个问，谁先答 `bridge=1` 就认谁：

1. `?bridge=http://127.0.0.1:8139` —— URL 上手工指定的（换端口调试就用它）；
2. 本页自己的来源（`start-debug.bat` 打开时走这条）；
3. `127.0.0.1` / `localhost` 的 `8123~8130`。

所以**用哪个地址打开都能连上**：桥托管的地址、别的本地服务器托管的、双击 `.html` 都行。
桥那边对应地要回 CORS 头（`Access-Control-Allow-Origin` 镜像回请求的 Origin，
不是 `*`），并实现 `do_OPTIONS` 预检 —— 少任何一边都不通。

> 原来这里写的是相对路径 `fetch("/api/status")`，只能同源用。症状是页面上
> 「没找到本地串口服务」而桥明明在跑；`file://` 下更离谱，相对路径被解析成
> `file:///C:/api/status`。修的时候两边都要动：页面改成绝对地址，桥补 CORS。

> 降级路径：桥不在时页面会明确告诉你去跑 `start-debug.bat`，并留一个「改用浏览器内置串口直连」的按钮。
> 那是真串口（Web Serial），不是模拟，只是要求 Chrome/Edge。

## 调试台怎么用

先双击 `start-debug.bat` 把桥起起来，浏览器打开它给的地址。底部 6 个页面按顺序走一遍就是完整流程。

**第 1 页不用做任何事**：桥会自动找到板子并连上，页面只是把状态画出来。

| 页面 | 做什么 | 过关标志 |
| --- | --- | --- |
| 1 连接 | 什么都不用点（自动扫描 + 自动连接）；确认档位是 `STS3032` | 顶栏「已连接 COMx」、状态块打绿勾、档位显示「正确」 |
| 2 编号 | **一次只插一个舵机**，轮流改成 1~6 号并贴标签 | 6 个进度点全绿 |
| 3 校准 | 先把 6 个舵机接回总线确认全在线，再采样活动手指；**3C 设拇指侧摆的「使能位」** | 顶栏「已校准」+ 使能位已记住 |
| 4 试动作 | 使能后逐个「按一下」，核对编号↔手指、按压方向；**顺手确认拇指两根轴谁是谁**（不对就一键对调） | 每根手指动作正确 |
| 4B 测响应速度 | 测 `PING` / `MOVE` 往返延迟，并连发 60 条压测 | 出结论：能不能跑到 6 Hz |
| 5 演奏 | 从**曲库**挑一首（L1~L5）或拖入自己的 MIDI，看分配预览与「音乐 ↔ 动作」卷帘图，调好速度/幅度/**行程时间**，点开始 | 手指**真的按得下去**、听得见完整音乐、卷帘上下对齐 |
| 6 日志 | 原始命令与回复，排查问题用 | — |

前置步骤没完成时，后续页面会被**闸门挡住**并提示先去哪一步，不会让人在错误状态下瞎点。

### 拇指那两根轴：一根按、一根摆位（第 3C / 第 4 步）

| | 按压轴（默认 slot0 / 舵机 1） | 侧摆轴（默认 slot1 / 舵机 2） |
| --- | --- | --- |
| 干什么 | 把拇指压到琴键上 | 把拇指摆到**能压到键的位置** |
| 参与演奏 | ✔ 每个音都动 | ✘ **全程只动一次**：开始演奏前到位 |
| 位置 | 松开位 ↔ 按到底（校准出来的整个行程） | 一个**试出来的「使能位」** |

- **第 4 步「两根轴对调」**：分别点 1 号、2 号的「按一下」，看拇指是往下压还是往旁边摆。
  出厂标签是反的（实测 slot0 才是按压），页面默认按 slot0=按压 走，不对就一键对调。
  **对调只换角色，不动舵机 ID、不作废校准**（校准是按槽位存的）。
- **第 3C 步「使能位」**：滑块（范围=该槽校准出来的侧摆行程）+「试这个位置」+「读当前位置」
  +「记住这个位置」。使能位是**试出来的**，没有公式 —— 指尖落在琴键正上方、往下压不打滑
  也不蹭邻键就是对的。存在浏览器本地（`槽位:位置`），**固件不需要改**。
- 演奏开始时自动摆到位（可关），暂停/正常结束时自动回松开位；急停不处理（断电就松了）。
- 没设过使能位也能正常演奏，只是拇指可能没对准。

## 4B 响应速度实测（决定演奏能跑多快）

**先测这个，再谈演奏。** 一次触键 = 按下 + 抬起两条命令，所以
「命令速率 = 动作频率 × 手指根数 × 2」。

| 口径 | 算式 | 结果 |
| --- | --- | --- |
| 协议硬指标（单指动作频率 ≥ 2 Hz） | 5 × 2 × 2 | **20 条/秒** |
| 快曲目标（6 Hz，软件可设 0~6 Hz） | 5 × 6 × 2 | **60 条/秒** |
| 内部工程目标（按全部 6 根留余量） | 6 × 6 × 2 | **72 条/秒** |

固件如果每条命令都要死等一个固定窗口，这个数就上不去。

三个按钮：

1. **测通信往返** —— `PING` × 20，不动舵机，最安全。拿到的是纯协议往返延迟
2. **测动作往返** —— `MOVE` × 20，含舵机动作开销（需先 ARM）
3. **压测** —— 不等回复连喷 60 条 `MOVE`（演奏页真实的工作方式），看固件会不会被压死、
   回复会不会丢；之后还会 `PING` 一次确认串口还活着

结果会直接给结论：**能跑满 6 Hz** / **需要降速到多少** / **必须改固件加原生命令**。

> 实现细节：`Transport.send()` 收到第一行回复后，只要 **140ms** 安静就立即返回，
> 不再死等 `timeoutMs`。计时写进 `T.last = {first, ms, lines}`，`first` 就是往返延迟。
> 这个改动同时让编号向导这类连续命令的操作快了一个数量级。
>
> 走本地桥时这套收尾逻辑在 `bridge.py` 的 `Bridge.send()` 里（同样是"第一行之后安静
> `quietMs` 就收工"），页面只是把 `first/ms/lines` 搬过来用 —— 所以测速卡和演奏调度的
> 判据在桥模式下没有变味。

## 演奏时序：四件事各管一段

用户原话是「有很严重的延迟，声音和动作不同步；按压时间长度也要加上啊；幅度也是；
最快的革命练习曲每个键都是抖动一下，根本没按下去」。逐条对应到实现：

| 症状 | 根因 | 在哪儿 |
| --- | --- | --- |
| 声音比动作早、越到后段越飘 | 一帧几十条 `MOVE` **逐条**走 HTTP，被浏览器同源并发上限（6 条）排队；声音是 Web Audio 当场同步发出的 | `Transport.fire()` 入队 + `flush()` 按 **`FIRE_TICK_MS=40ms`** 合并成一批；桥侧 `/api/fire` 收 `{cmds:[…]}` 一次 `write` |
| 每个键「抖一下、没按下去」 | 按住时长按**曲谱**毫秒算，200% 速度下只剩 30ms 真实时间，而舵机走完一次行程要 ~90ms | `buildPlan(notes, mode, speed)` 里所有物理约束改用**真实毫秒**，再乘 `k` 换回曲谱时间 |
| 每个音都一样长、短平快 | 按住时长被夹成 `clamp(n.d*0.8, 55, 200)`，长音也按 200ms | 同上：`holdReal = max(stroke, min(音符时值真实毫秒×0.9, MAX_HOLD_MS))` |
| 幅度看不出区别 | 力度映射写成 `max(0.35, vel)`，弱音几乎不动 | `ampOf(vel) = 0.45 + 0.55×vel`：底 45% 保证弱音也看得见，上限 1.0 = 用满校准行程 |
| 快曲「音乐对不上」 | 声音时长传的是**曲谱**毫秒，200% 下每个音拖两倍长、糊成一片 | `tone()` 收 `e.holdReal`（真实毫秒）而不是 `e.durMs` |

两个**容易忽略但必须守**的细节：

- **「手指行程时间」（`strokeMs()`，默认 90ms）是一个真旋钮，不是装饰。**
  它既是「按到底要多久」，也是「同一根手指多久才能再用」——
  `busyUntil[slot]` 必须记 `(holdReal + stroke) × k`，因为**松开也要时间**。
  只记 `hold` 等于默认"松开是瞬移"，下一个音立刻又来、按到一半就被反向拉走，
  连击就糊成一团。默认 90ms 来自实机测速：满行程一次完整按压 4.97Hz ≈ 201ms，单程是一半。
- **速度一变就必须重算 plan**（`#speed` 的 `onchange` → `analyze()`）。
  plan 里的物理约束都按真实毫秒算，速度换了不重算，「按到底」的判断就还停在旧速度上。
  拖动时只更新文字、松手才重算 —— 重算要遍历整曲，跟着 `input` 每帧跑会卡。

丢音是**物理必然**（能按琴键的只有 5 根，快曲必然按不过来），所以界面上直接写「这首曲子 N 个音按不了」，
默认把那些音**只用声音补齐**（手指不动）。以前这个开关点了没感觉，
就是因为看不见丢了几个 —— 而 L1~L3 的曲子本来就一个不丢。

另外：演奏期间**不逐条写日志**。整曲 480 条命令就是 480 次 DOM 追加，
主线程被日志拖住 → rAF 掉帧 → 动作看着更抖。停止后补一条摘要，写明
「N 条命令 → 合并成 M 批（单批最多 K 条）」。

## 演奏页（MIDI → 手套）

- 支持 **format 0 / 1** 的 `.mid`，自动处理 running status、变速（tempo map）、SMPTE 时基
- 两种分配方式：
  - **轮流分配**（默认）—— 把音符依次分给当时空闲的手指，节奏最完整、手指动得最均匀
  - **音高对应** —— 把本曲的**实际音域**均分给参与演奏的槽位，低音偏拇指侧、高音偏小指侧。
    音域窄的曲子（比如只用 6 个音的《小星星》）会**一个音一根手指**
- 可按轨道 / 通道 / 音域筛选（钢琴曲通常只弹右手主旋律）
- 导入后会**预估峰值命令速率**并提示。手套能按琴键的只有 5 根，音比手多时主动丢音保节奏，不会卡住不动
- 按住时长取音符时长的 80%（夹在 55~200ms），接近真人触键。**这条是"音符密≠难"的原因**：
  触键只占 55~200ms，5 根手指轮转足够，单声部旋律再快也压不垮；真正吃紧的是同一时刻要几根手指
- **演奏一结束就给全部舵机断电**（固件 `DISARM`），默认开、可取消 ——
  见下面[「演奏结束：全部舵机失能」](#演奏结束全部舵机失能奏完失能默认开)

### 演奏速度分级（越高级越快）

曲库每首自带**本级建议速度**，选中即自动套用 —— 级别越高跑得越快：

| 级别 | 建议速度 |
| --- | ---: |
| L1 入门 | 90% |
| L2 简单 | 110% |
| L3 初级 | 140% |
| L4 中级 | 170% |
| L5 挑战 | 200%（**故意超过手套上限**，压力测试用） |

速度滑块可以自己拖，上限 **250%**；旁边那个 **⚡ 拉满** 一键压到顶。
滑块下面那行会实时算出「当前速度相当于手套上限的几倍、大概多少动作发得出去」——
**「极限在哪」是个看得见的数字，不用凭感觉**。

> ⚠️ **「越高级越快」是按倍率说的，不是按绝对频率。** 实际按压频率还受曲子本身密度影响：
> 卡农每音两拍、24 个音铺满 35 秒，即使给它 L4 的 170%，也只有 1.2 次/秒，
> 比《小星星》还慢 —— 那是谱子决定的，不是分级没生效。
> 逐首的实测频率见 [`samples/FINGERING.md`](samples/FINGERING.md) 的「演奏速度分级」表（脚本生成，可对账）。

### 音乐 ↔ 演奏动作 同轴显示

演奏页下方那张图，上半张是**曲子本身**（横轴时间、纵轴音高），下半张是**手套的动作**（一行一根参与演奏的手指），
两块共用同一条时间轴、同一根播放头。同一根手指用同一种颜色 —— 上下对齐看，就知道每个音是哪根手指按的。

- **声音是浏览器现场合成的**（Web Audio：三角波基频 + 一点二次谐波，快起 + 指数衰减），
  不需要额外的音频文件。默认只响手套**真的按下去**的那些音，所以「听到的 = 看到的 = 手套做的」三者一致
  —— 声音和动作是**同一条事件流**发出来的，不存在"音频跟动作对不齐"。
- 勾上「连被丢掉的音也一起响」可以把丢音补响，用来对比「完整曲子」和「手套演奏」差多少。
- **灰色小块 = 手套来不及按、被丢掉的音**（能按琴键的只有 5 根，保节奏优先）。它只画在上半张，
  因为它没有对应的动作。
- 窗口模式有**整曲总览**和**跟随播放头**（8 秒窗口）两种，长曲子用跟随才看得清。
- 导入 MIDI 后**不用按播放就已经画出总览** —— 可以先看「这首曲子手套要做什么、哪些音它按不了」。

### 声音什么时候响？——起音点 + 音画对齐

用户前后反馈过两次，合起来才说清这件事：

1. 「舵机按下去感觉要过一会声音才会响，没有那种声音是从手指按下触发的感觉」
2. 「应该在按下行程的一半就发出声音，这跟弹钢琴也是一样的啊」

第 2 条定了**目标**：出声时刻不是"手指一动"，而是"手指走到行程的一半"——
真钢琴也是压到中段击弦，不是等琴键按到底。第 1 条定了**要实现它得先补什么**：
WebAudio 从 `ctx.currentTime` 到真正出声，中间还要过 `baseLatency`（渲染送出）
+ `outputLatency`（设备缓冲）—— 本机实测 **10 + 40 = 50ms**，
再加 `tone()` 自带的 10ms 调度提前量，一共 **60ms** 的固定延迟（不是越拖越慢）。

于是出声时刻就一条式子（全部真实毫秒）：

```
提交时刻 = 按下时刻 + 行程 × 起音点 − 声卡延迟
```

起音点把声音**往后推**（行程一半 ≈ 45ms），声卡延迟把它**往前拉**（60ms），
两者相抵才是耳朵听到的落点。默认参数下净效果是**提前 15ms** 提交。

演奏页「试听一下」下面有两行控件，都存浏览器里：

| 控件 | 默认 | 干什么 |
|---|---|---|
| **起音点** | 行程 50% | 声音落在手指行程的百分之多少处。`0%` = 手指一动就响，`90%` = 快按到底才响 |
| **音画对齐** | 实测 + 微调 | 在起音点之上做最后的微调（±60ms）。自动读的是声卡自报的延迟，不同驱动 / 蓝牙耳机未必准，最后还得耳朵说了算 |

再下面那行「声音落点」会把三个数一起摊开，例如：

> 声音落点：手指走到 **45ms**（行程 50%）时出声 │ 声卡 **60ms** │ 提交时刻 **提前 15ms**

**卷帘图上看得见**：下半张每根手指的动作条上有一道细刻度，就是声音落点。
条宽 = 这一按的真实时长，所以长音上刻度靠在最左边（一按就响、然后一直按住），
短音上正好落在中段 —— 不用靠耳朵猜「声音到底在动作的哪一刻响」。

想知道自己这台机器该补多少：

```bash
node host/tests/diag_audio.js                    # 无头也能量
set HEADED=1 && node host/tests/diag_audio.js    # 有头：走真实声卡
```

> **为什么声音要用独立的游标推进**：声音和动作的触发条件不再是同一件事了
> （声音要按 `t + 行程×起音点 − 声卡延迟` 算，动作按 `t` 算），两者不能共用一个游标。
> 也正因为如此，「起音数 == 动作已发出的按下数」这种比较在**稀疏曲子**上会假绿
> —— 小星星的音符间隔是 3.3 秒，几十毫秒的窗口里根本没有第二个音。
> 自测里改用**密集曲**（革命练习曲，真实间隔 188ms）逐个音比对提交时刻，
> 并特意把「手指行程时间」拉到 200ms 再做 —— 让 `行程×起音点 = 100ms` 远大于
> 一帧的量化误差（16.7ms）。用默认 90ms 时预期提前量才 −40ms，
> 和"完全没减行程"只差 45ms，被帧量化吃掉一半就滑进容差里 —— 又是一个假绿。
> 两处变异（砍声卡延迟 / 砍起音点）分别对应上面两条用户反馈，确认都会红。

**听不到声音怎么排**：演奏页有「🔔 试听一下」按钮，右边还有一行音频状态，按这个顺序看：

1. **试听有声、演奏无声** → 检查「播放声音」有没有勾上；再看一眼播放速度是不是拉得太高
   （速度很快时音符会糊成一片）
2. **试听也没声** → 点一下「试听一下」。浏览器的自动播放策略要求音频**必须由一次点击启动**，
   那一下点击就是解锁动作；解锁失败时状态行会直接写明「被浏览器拦住」。
   另外页面上**任何一次点击**都会顺手解锁音频，所以正常走完流程（点连接、点校准）早就解锁了
3. **还是没声** → 大概率是预览面板静音、或系统没接音频输出设备。
   双击 `start-debug.bat` 换成 Chrome 打开同一个地址再试

### 演奏结束：全部舵机失能（「奏完失能」，默认开）

演奏页「开始演奏」那一行有个 **「奏完失能」** 勾选框，默认**勾上**：
**曲子一结束（自然奏完，或中途按 ▶ 暂停停掉）就给全部舵机断电** —— 发固件那条
`DISARM`（= 取消使能 `armed=0` + `torqueAll(false)` 全部卸力）。

为什么结束必须断电：

- 演奏完了手指还带电按在琴键上 —— 舵机一直出力顶着、发烫、耗电，几根手指还会互相较劲；
- 演奏一结束人就要上手戴/摘手套，**带电的舵机被人手硬掰会顶伤齿轮**。

顺序是**先**把拇指侧摆送回松开位、**后**断电。理由在固件里：`DISARM` 之后 `MOVE`
一律回 `motion_not_armed`，倒过来的话那条回位命令等于白跑，拇指会停在"对准琴键"的
使能位上，手套戴着别扭。手指那五根不用单独放：曲子末尾的 `off` 事件已经把它们放开了，
中途停的话断完电它们也会自己垂下来。

| 你按的 | 发什么 | 结果 |
| --- | --- | --- |
| 曲子自己奏完 | `DISARM` | 全部舵机失能，手指自然松开 |
| ▶ 暂停（演奏中再点一下） | `DISARM` | 同上 |
| ■ 停止（红色急停） | `SAFE` | 停扫速 + 全部断电，比 DISARM 更狠，这条路**本来就**断电 |
| 取消勾选「奏完失能」 | 只发侧摆回位 | 保持带电（想连着弹下一首时用） |

**断电后不必回第 4 步手动点「使能」**：▶ 开始演奏时会自己重新 `ARM`（急停那条路也一样）。
（页面为此记了个本地标记 `S.needArm` —— `S.info.armed` 是发 `INFO` 查回来的，
断电到下次查询之间那几百毫秒里它是**旧值**，光看它会以为还使能着，
那样刚发的 `MOVE` 会全被固件回 `motion_not_armed`，手指一动不动。
两条断电的路都要记这一笔：按完 ■ 停止 400ms 内再按 ▶ 也是常见操作。）

另外还有一层兜底：**演奏进行中**直接关掉页面 / 刷新，也会补发一条 `DISARM`
（用 `keepalive` 的 `fetch`，页面被别的本地服务器托管时也发得出去）。
只在演奏中才发 —— 平时（比如校准完特意把手指摆在某处细看）关页面不该被偷偷断电。

## 快速开始

```bash
pip install -r requirements.txt

python glove_fw.py info                  # 固件 / 档位 / 校准 / armed
python glove_fw.py assign                # 逐个把舵机 ID 编成 1~6
python glove_fw.py auto                  # 固件自检，action= 字段含诊断建议
python glove_fw.py status                # 6 槽位总表
python glove_fw.py cal wizard 20         # 一键校准向导
python glove_fw.py monitor               # 轮询实时反馈
python glove_fw.py raw "CAL STATUS"      # 发任意命令
```

板子串口**自动识别**（挨个串口发 `INFO`，谁回 `OK INFO` 就是它）。串口号会随 USB 枚举变化，所以别写死；要指定就 `--port COMx`。

网页调试台：

```bash
python bridge.py                       # 起串口桥（自动扫描 + 自动连接），127.0.0.1:8123
# 浏览器打开 http://127.0.0.1:8123/web_piano_glove.html
# 或者直接双击 start-debug.bat，它会顺带把 pyserial 装上、把浏览器打开

python bridge.py --url COM4            # 写死某个串口
python bridge.py --no-auto             # 只提供 API，不自动连（手动用 /api/connect）
```

波特率固定 **115200**。

## 写客户端时要注意的几条

- **串口会因 USB 重新枚举而失效**：Python 侧报 `ClearCommError failed (PermissionError 13)` 或 `FileNotFoundError(2)`。前者=端口句柄失效，后者=设备消失。健壮客户端应捕获 `serial.SerialException` → 关端口 → 循环重开。
- **不要发广播 `PING 254`**：某些 SDK/固件在此路径会返回空包导致崩溃。
- **`SETID` 报 `write_or_verify_failed` 不等于失败**：常见于写入成功但复核赶上舵机重启空窗。判据应为「稍等后 `PING <new_id>` 是否通」。
- **轮询别刷太猛**：遍历 10 个 ID ≈ 6 秒，自动刷新建议 2~3 秒一次。

## legacy/ 里的东西为什么不能用

`web_debug.html` 与 `glove_calibration.py` 是**早期版本**，直连 Feetech SCS 原始协议，本意是「PC 直连舵机总线」。但当前主控固件 **`PIANO_GLOVE_1` 没有串口透传功能**，所以这两套工具在现有硬件上发什么都没反应。

保留原因：`web_debug.html` 里有**手指 SVG 动画、示波器、跟随误差评估、calib.json 导入导出**，是很好的 UI 素材，扩展网页调试台时可直接借鉴。

复活条件：把板子刷成微雪官方 ST 系列固件并打开 `SERIAL_FORWARDING`（串口透传）。
