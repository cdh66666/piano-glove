# tests · 自测与实机验证

分三类：

| 类别 | 需要板子？ | 干嘛的 |
| --- | --- | --- |
| **串口桥自测** | ❌ 不用 | 真 `bridge.py` 进程 + 假板子（TCP 装串口），验「自动选推荐口 / 自动连接 / 长轮询 / 跨站拦截」 |
| **页面端到端** | ❌ 不用 | 用页面内置假固件顶替串口（`?sim=1`），把「编号 → 校准 → 试动作 → MIDI 演奏」整条链路跑一遍，并反过来验「页面上没有模拟模式、打开就自动连上」 |
| **实机验证** | ✅ 要 | 直接对板子发指令、读回包，用**数字**回答「舵机到底动没动、能跑多快」 |

前两类都用真实浏览器（Chromium）打开页面、点按钮、检查结果，用来在接硬件之前确认界面没坏。
实机那一侧不猜、只量 —— 发指令前后各读一次位置，比差值。

## 依赖

```bash
pip install pyserial          # bridge.py / bridge_check.py / 实机脚本需要（start-debug.bat 会自动装）
npm i playwright-core         # 浏览器驱动
npx playwright install chromium   # 或者用系统已有的 Chrome，设 CHROME_PATH 环境变量
```

## 跑法

```bash
cd host/tests

# 1) 交叉验证 MIDI 解析器：网页端 vs 独立 Python 参考实现，逐音符比对
python make_midi.py       # 生成测试用 MIDI（含 format 1 / format 0 两份）
python ref_parse.py       # 参考实现解析 -> ref.json
node compare.js           # 两边结果比对

# 2) 串口桥自测（真进程 + 假板子，无需硬件）
python bridge_check.py    # 输出 43 项 PASS/FAIL

# 3) 页面端到端自测（内置假固件，无需硬件）
node e2e.js               # 输出 207 项 PASS/FAIL（结尾由脚本自报总数），截图存到 shots/

# 4) 往"桥"那条路上注入退化，确认对应断言真的会变红
node mutate_bridge.js

# 5) 往"演奏时序"那条路上注入退化（16 处），确认对应断言真的会变红（约 32 分钟）
#    只跑其中几处：node mutate_play.js 使能位   （按名字里的片段筛）
node mutate_play.js

# 6) 演奏时序诊断：把「抖动」变成数字（按住时长、同手指间隔、行程时间扫描）
node diag_timing.js
node diag_timing.js revolutionary moonlight     # 只跑指定曲目

# 6b) 音频输出延迟诊断：量「决定发声 → 真正听到」这段固定延迟（音画对齐补的就是它）
node diag_audio.js
set HEADED=1 && node diag_audio.js             # 开真窗口，走真实声卡

# 7) 关键页面视觉抽查（视口截图 + 窄屏横向滚动检查）
node shots.js
```

`diag_timing.js` 是改参数前**必须先跑**的那个：它会告诉你「同一根手指两次按下
隔了多久」「按住时长够不够舵机走完行程」「行程时间拧到多少会丢掉多少音」。
「最快的革命练习曲每个键都抖一下」这个 bug 就是它量化出来的 ——
改参数前实测 200% 下按住只剩 **30ms**，而行程要 90ms。

`diag_audio.js` 量的是另一件事：**音频链的固定延迟**。
用户说的「舵机按下去要过一会声音才响、没有按下触发的感觉」就是它量出来的 ——
本机实测 `baseLatency 10ms + outputLatency 40ms + tone() 自带 10ms = 60ms`。
但**这个数不是出声时刻**，只是算式里的一项：
出声时刻 = 按下时刻 + 行程×起音点 − 声卡延迟（见 `web_piano_glove.html` 的「起音点」滑块）。
用户第二轮把它点明了：「应该在按下行程的一半就发出声音，跟弹钢琴一样」。
换了声卡 / 插上蓝牙耳机之后，想知道声卡这一项该补多少就再跑一次。

`shots.js` 里 `v7d-attack-tick.png` 用的是**元素截图**而不是视口截图 ——
卷帘图动作条上那道起音刻度只有 1px 宽，缩进整页图里根本看不清，
而它是"声音在动作的哪一刻响"唯一能看的凭证。
e2e 跑完留下的 `08d-disarm.png` 是演奏页收尾那一段（含「奏完失能」开关）。

`CHROME_PATH=/path/to/chrome node e2e.js` 可以指定浏览器。
`PYTHON=/path/to/python python bridge_check.py` 可以指定解释器（默认跟随 `sys.executable`，
`e2e.js` 在 Windows 上默认用本机的托管运行时，可用 `PYTHON` 环境变量覆盖）。

### 假板子是怎么回事

`fake_glove.py` 是一个说手套文本协议的 TCP 服务。pyserial 支持 `socket://host:port`
这种「串口 URL」，所以 `bridge.py --url socket://127.0.0.1:9701` 就能把 TCP 当串口用。

于是 `bridge_check.py` 里**假的东西只有"对面那块板子"**：真 bridge 进程、真 HTTP、
真 pyserial、真收发线程、真长轮询。这比"把桥也 mock 掉"值钱得多 ——
`/api/lines` 能不能捞到延迟吐出的 `RATE_DONE`，只有这样才测得出来。

它故意**不**照抄页面里那份 `MockFirmware`：那份服务于"没有串口的页面级自测"，
这份服务于"真串口链路"，两者假的东西不一样，重复是必要的。

### 实机（插上板子和舵机）

```bash
# 读一遍板子落在 NVS 里的真实状态（编号结果 / 校准值 / 总线诊断）
python diag_state.py            # 自动找板子；也可 python diag_state.py COM3

# 验「舵机真的动了」+ 测速 —— 主力脚本
python bench_move.py                 # 全部槽位：先读位置、发 MOVE、再读位置、比差值
python bench_move.py --slot 1,2,3    # 只测某几根（1 起编号）
python bench_move.py --no-move       # 只看状态，一条 MOVE 都不发
python bench_move.py --force         # 强行测「校准可疑」的槽位（默认跳过）

# 串口枚举 + 逐个试着打开，把打不开的原因说清楚
python probe_open.py
```

**`bench_move.py` 的两道安全闸**（别绕过）：

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `POS_TOL` | 30 计数 | 位移小于这个数就算「没动」，避免把抖动当成功 |
| `CAL_SUSPECT` | 600 计数 | 校准记录的静止位与舵机**当前实际**位置差超过这个数 → 判定「这份校准不是这块舵机的」，**默认跳过不动**，要测必须 `--force` |

这道 `CAL_SUSPECT` 闸是真起过作用的：它先报出「槽位 0 的校准数据不是 1 号舵机的」（差 1309 计数），
才有了后来那个编号映射 bug 的定位。详见 [`../../docs/design-notes.md`](../../docs/design-notes.md) 风险 9。

### 生成演奏样本

```bash
python make_samples.py          # 10 首分级样本 -> host/samples/，并自动内嵌进调试台曲库
python make_samples.py --list   # 只看清单，不写任何文件
python make_two_tigers.py       # -> host/samples/two-tigers.mid（362 B / 32 音符）
python check_midi.py            # 结构校验：头、MTrk 长度、事件数、末尾完整性
node   fingering_report.js      # 导出 host/samples/FINGERING.md 自动指法表
```

`make_samples.py` 生成的每个 `.mid` 都**不含指法信息**（只有曲名/速度/拍号/音符），
所以它生成完会立刻解析自己写的文件，扫出所有 meta 类型，发现 `Text(0x01)` / 歌词(0x05)
之类就报错退出。e2e 里也有一条对应的断言，用的是同一套判据。

## 各文件做什么

| 文件 | 说明 |
| --- | --- |
| `make_midi.py` | 生成测试 MIDI。故意包含 **running status**、多轨、变速、密集快速音、五音和弦 —— 覆盖解析器最容易出错的分支 |
| `ref_parse.py` | **独立写的** MIDI 参考解析器（Python）。两边独立实现，结果一致才说明网页端解析器是对的 |
| `compare.js` | 逐音符比对网页端解析器与参考实现的时间/音高/时长/力度 |
| `e2e.js` | 页面端到端自测：连接 → 6 轮编号 → 校准 → 使能 → 单指测试 → 4C 测速 → MIDI 演奏（含音乐↔动作卷帘）→ 日志 → **第 8 节真桥自动连接**，并检查全程无 JS 报错 |
| `bridge_check.py` | 串口桥自测：推荐口打分、自动选口决策顺序、HTTP 接口、长轮询异步行、跨站拦截、断开语义 |
| `fake_glove.py` | 假手套：TCP 说手套文本协议，供 pyserial 的 `socket://` 接进来 |
| `mutate_bridge.js` | 变异测试：往"桥"那条路注入 3 处退化，确认对应的 5 条断言都会变红 |
| `mutate_play.js` | 变异测试：往"演奏时序"注入 16 处退化（命令不聚合 / 按住无下界 / 槽位不算松开 / 幅度不跟力度 / 行程旋钮不接线 / 声音用曲谱时长 / 补齐开关失效 / **侧摆被算成能按琴键的手指** / **演奏前不摆使能位** / **使能位不核对槽位** / **声卡延迟不补偿** / **起音点被忽略** / **只朝本页来源找桥** / **演奏结束不失能** / **收尾顺序反了** / **急停后不记待使能**），逐条确认对应断言变红 |
| `diag_timing.js` | **演奏时序诊断**：读页面里真实的 `S.plan`，算出按住时长、同手指相邻按下间隔、各手指负载，并扫描「行程时间 → 丢音数」。改演奏参数前先跑它，别拍脑袋 |
| `diag_audio.js` | **音频输出延迟诊断**：量 `baseLatency` + `outputLatency`，给出「决定发声 → 真的听到」这段固定延迟，以及页面实际补了多少。换声卡 / 蓝牙耳机之后跑它 |
| `shots.js` | 关键页面视觉抽查 |
| `bench_move.py` | **实机主力脚本**。验位移 + 测速；带两道安全闸（见上） |
| `diag_state.py` | 读板子真实状态：`INFO` / `CAL STATUS` / `STATUS_ALL` / `BUSINFO` |
| `probe_open.py` | 串口枚举 + 逐个试开，报出打不开的具体原因 |
| `make_two_tigers.py` | 生成《两只老虎》演奏样本 |
| `make_samples.py` | 生成 **10 首分级演奏样本**（L1~L5）+ `catalog.json`，并把曲库内嵌进 `web_piano_glove.html`。自带「无指法」自检 |
| `fingering_report.js` | 驱动真实浏览器跑**页面里那一份** `buildPlan()`，导出 `samples/FINGERING.md` 自动指法表 |
| `check_midi.py` | MIDI 结构校验（头字段、`MTrk` 声明长度 vs 实际剩余、事件完整性） |

### `e2e.js` 里几条「反直觉但必须保留」的断言

改这个文件时别顺手把它们简化掉：

1. **槽位映射不看界面文案，直接读固件映射。** 发 `STATUS_ALL`，解析出的槽位 id 序列必须等于
   `1,2,3,4,5,6`。编号 bug 期间界面一路显示「编号完成」而实际是 `[2,2,3,4,5,6]` ——
   凡是断言界面文案的写法都抓不到它。**做过变异测试**：把修复退掉，这条立刻变红。
2. **深度条要多次采样取峰值，不能只读一次。** 无头浏览器 `requestAnimationFrame` 大约只有 8 fps，
   「按下 + 抬起」可能落在同一帧里，单次读取会偶发全 0。现在是连采 14 次（间隔 80 ms）取每个手指的最大值。
3. **卷帘图的颜色断言只能在「不播放」时采样。** 播放时已播区域会压一层 `rgba(26,110,240,.07)` 的半透明蓝，
   把底下的纯色染偏，严格的颜色匹配会全部落空（会误报成「一根手指都没画」）。
4. **「停止后音频节点被清空」必须在播放中直接调 `stopPlay()` 并立刻读。** 晚读几百毫秒的话，
   短音符自己就 `ended` 出队了，**把 `silence()` 整段删掉也测不出来**（假绿）。
   第一次做变异测试时就是被这个骗过：三处退化一起注入，另两处让 `tone()` 根本没被调用，
   音频数组本来就是空的，这条自然"通过"；单独注入 `silence()` 才暴露（剩余节点 2 → 变红）。
5. **「丢音灰影」要用注入法验，不能指望现成素材。** `test.mid`（85 音符 / 6 秒）均摊到 6 根手指
   其实 `dropped = 0`，直接断言「有丢音」会失败得很冤枉。现在的写法是：先注入一批 `droppedNotes`
   验证会画灰影，还原后再确认「没丢音时图上干净」—— 两条互为对照。
6. **「样本不含指法」这种承诺要靠解析证明，不能靠"生成的时候看过一眼"。**
   指法在 MIDI 里最常见的藏身处是 Text（0x01）和歌词（0x05），人打开播放器根本看不出来。
   断言扫的是**全部 meta 类型**，只放行 0x03/0x51/0x58/0x2F。
   **做过变异测试**：往 `twinkle.mid` 里塞一个 `finger:thumb` 的 Text 事件，
   断言立刻报 `twinkle:0x1` —— 连是哪种 meta 都指出来了。
7. **起音点 / 音画对齐要用密集曲、逐个音比对「提交时刻」—— 只数音符个数会假绿。**
   出声时刻是一条式子（全真实毫秒）：`提交时刻 = 按下时刻 + 行程×起音点 − 声卡延迟`。
   于是声音由**自己的游标**推进，和动作游标不再同步。
   原先那条「起音数 == 已发出的按下数」在稀疏曲子上恰好相等、侥幸为真 ——
   小星星的音符间隔是 3.3 秒，几十毫秒的窗口里根本没有第二个音，怎么写都是绿的。
   现在换革命练习曲（真实间隔 188ms）**逐个音**比对「提交时刻」与
   「该音在曲谱里的理论时刻」，实测提前量中位必须对得上式子算出来的预期值。
   ⚠️ **测这个必须先把「手指行程时间」拉到 200ms。** 默认 90ms 时
   `行程×起音点` 才 45ms，预期提前量 −40ms 与"完全没减行程"只差 45ms，
   被一帧的量化误差（16.7ms）吃掉一半就滑进容差里 —— 又是一个假绿。
   拉到 200ms 后 `行程×起音点 = 100ms`，两个变异各自差 60 / 100ms，稳稳咬住。
   另外用例里有一条**前提断言**先卡住"行程×起音点 ≥ 60ms"，
   免得有人把行程改小之后这条悄悄退化成永远为真。
   **做过变异测试**：① 砍声卡延迟补偿；② 砍起音点 —— 两条都变红。
8. **内嵌曲库要逐字节比对，不能只验「能不能加载」。** 网页里的 base64 由脚本生成，
   很容易和磁盘文件悄悄脱节（改了生成脚本、忘了重跑）。断言用 `Buffer.equals` 逐字节比，
   并且「网页清单 ↔ `samples/` 目录 ↔ `catalog.json`」三者要一一对应。
   **做过变异测试**：只改动磁盘上的 `twinkle.mid`，这条立刻变成 `9/10`。
9. **音高对应模式要断言「用满全部参与演奏的手指」，不能只看"有没有输出"。**
   这个 bug 藏了很久：`hi` 兜底到 72、`want` 用 `floor(ratio*6)`，导致《小星星》的
   C D E F G A 只占满 **4 根**手指（E/F 挤在食指、小指全程闲着）—— 而这首曲子当初被选进
   样本库的理由恰恰是「6 个音 = 6 根手指」。**做过变异测试**：退掉修复，断言返回
   `[6,6,16,10,4,0]` 立刻变红。另外还配了一条「音越高、手指越靠小指侧」保证单调性。
   ⚠️ **2026-09-20 起分母是 `PLAY_SLOTS.length`（默认 5），不是字面量 6** ——
   拇指侧摆不参与演奏（见第 12 条）。
10. **音频断言不能只读 `AudioContext.state` —— 那是假绿。** headless Chromium 里
   `AudioContext` 一建出来就是 `running`，所以「断言 state === running」永远成立，
   把演奏入口那行 `unlockAudio()` 整行删掉也测不出来。现在改成**包一层数调用次数**，
   删掉调用立刻变红。**做过变异测试**：4 处退化一起注入 → 5 条断言变红，
   其中这条报 `n:0` 而 `state` 仍是 `running`，正好印证了"读 state 什么都测不到"。
11. **「越高级越快」要断言真实的频率数字，不能只断言速度标签。** 断言读的是页面提示里的
    「约 X 次按压/秒」（由 `peakRate × 当前速度` 算出来），并要求 L5 > L1。
   **做过变异测试**：把分级退化成「不管哪级都 100%」，
   「选 L1 自动套用 90%」「选 L5 自动套用 200%」两条立刻变红。

12. **拇指侧摆：三件事必须各有断言（2026-09-20 加）。**
   - **不给它派活**：断言侧摆槽位分到 0 个音、卷帘图上它的颜色一个像素都没有。
     变异「把 `PLAY_SLOTS` 改成全部 6 根」→ 立刻变红。
   - **演奏前只发一条命令**：把 `T.mock.handle` 包一层记下所有命令，
     断言演奏开始那一段里发给侧摆 id 的 `MOVE` **恰好一条**、且位置 = 使能位；
     暂停后再发一条、位置 = 松开位。变异「开始时不调 `latchEngage(true)`」→ 变红。
   - **使能位必须绑槽位**：存的是 `"<slot>:<pos>"`。断言"对调角色后旧值作废"。
     变异「`latchPos()` 不再核对槽位」→ 变红。
     为什么这条值钱：不绑槽位的话，用户一对调角色，旧位置就会用在量程完全不同的另一根轴上。
13. **深度条采样要按 `data-slot` 取，不能按下标取。** 侧摆那一行也在 `#p-play .dep` 里
   （它显示的是"使能位"，不是深度），按下标取会把它当成一根手指、深度恒 0 ——
   两条"深度落在合理区间"的断言会平白变红。
14. **演奏收尾：四条路 + 顺序 + 查询空窗都要验（2026-09-20 加）。**
   用户原话「还有演奏完之后就要全部舵机失能」。要验的是**收尾那一刻**发出的命令，
   所以把 `T.mock.handle` 包一层记命令，**只记非 `MOVE` + 侧摆那条 `MOVE`**
   （整曲几百条手指 `MOVE`，全记下来失败信息就没法看）：
   - **① 自然奏完**：断言 `#planMsg` 出现「演奏结束」+ 收到 `DISARM` + 板子 `armed=0`。
     变异「收尾不发 `DISARM`」→ 立刻变红。
   - **② 顺序**：`DISARM` 的下标必须**大于**侧摆回位那条 `MOVE` 的下标。
     变异「先断电、再回位」→ 只有这条变红（不连坐 ①，两条断言各自都证明了自己在测东西）。
     为什么值钱：固件里 `DISARM` 之后 `MOVE` 一律回 `motion_not_armed`，
     顺序反了那条回位命令就白跑，拇指停在"对准琴键"的使能位上摘不下来。
   - **③ 反向**：关掉「奏完失能」时必须 `armed=1`、且**没有** `DISARM`、只有回位命令。
   - **④ 急停（■ 停止）也是断电**：它走 `SAFE`，同样要记「待重新使能」。
     断言在 `refreshInfo`（400ms）**之前**读 `S.needArm` / `armed`，读的就是那段空窗。
     变异「急停后不记待使能」→ 变红。**别只补 `finishPlay()` 那一条路** ——
     两条路都是"板子断了电、页面还不知道"，bug 一模一样。
   - **查询空窗（在 ② 用例里一起验）**：`S.info.armed` 是发 `INFO` 查回来的，
     断电到下次查询之间那几百毫秒它是**旧值**。所以 e2e 里**故意**把 `S.info.armed`
     伪造成 `"1"` 再按播放，断言这一下仍然发出 `ARM` —— 这才是 `S.needArm` 存在的理由。
     不伪造的话 ① 结束时那次 `refreshInfo` 已经把 armed 刷成 0 了，
     这条就退化成"因为没使能所以 ARM"，`S.needArm` 整行删掉也照样绿。
   - **别在 `begin()` 之后清空命令缓冲区**：一清就把自动 `ARM` 洗掉了，看起来像"没发送能"（踩过）。
   - **怎么不干等**：用最短的曲子（致爱丽丝 12 秒）再点「拉满」顶到 250%，实测约 5 秒跑完。

## 已知的坑（写脚本时踩过）

- **演奏页的控件行在窄屏会悄悄折行 —— 加控件前先量，别等用户看见。**
  「开始演奏 / 停止 / 循环」那一行再塞第 4 个元素后，**360px** 视口下
  「▶ 开始演奏」被挤成两行（按钮高 44 → 89px），430px 才放得下。
  结论：「奏完失能」单独占一行。**量的时候有个陷阱**：演奏页在校准前
  `#playBody` 是 `display:none`、载入曲子前 `#midiPanel` 也是，
  `getBoundingClientRect()` 会**整片返回 0**（不是报错，看着像"没溢出"）。
  临时从目标元素往上把 `display:none` 的祖先掀开再量。

- **顶层初始化不要调用依赖后面 `const` 的函数**（TDZ）。`LEVEL_SPEED` 曾经声明在文件后半段，
  而顶层那句 `applyLevelSpeed(SONG_LIB[0])` 在它之前执行 → 抛
  `Cannot access 'LEVEL_SPEED' before initialization`，**整个顶层脚本从那行断掉**，
  后面的事件绑定（含 `#songLib.onchange`）全部作废。症状是「曲库下拉换了没反应」，
  而 e2e 报出来的是「两条曲库断言 FAIL + 一条页面导航错误」，很难一眼看出是 TDZ。
  **规则：常量一律声明在所有使用它们的代码之前。**
- **`mutate_play.js` 会把源码改坏再跑；它被杀掉时源码就留在"改坏"状态。**
  真事：一次外层超时把脚本 SIGTERM 掉，`finally` 来不及还原，
  `holdReal` 的下界就那样留在了磁盘上，下一轮报"变异点找不到"。
  所以脚本开跑前把原文件存成 `.mutbak`、跑完删掉；**启动时看到 `.mutbak` 就先还原**。
  三条加固（都踩过才知道要加）：
  1. **还原以磁盘备份为准（`copyFileSync`），不用内存里那份字符串。**
     内存还原 + 反复被 kill 的组合会发生这种事：我手动 `cp` 回来一次，
     下一轮又被 kill，源码就带着第 7 处变异（`if(false && S.plan.droppedNotes)`）
     继续往下开发 —— 改文案、跑截图、写文档，全程没人发现。
     最后是 e2e 里那条「补齐按不了的音」真的多出声把它抓出来的。
     **内存里的字符串和磁盘上的文件是两回事。**
  2. **开跑前 + 收尾后各做一次源码自检**（`verifyClean()`）：逐条确认 16 处变异点
     都还在正常状态，缺任何一处就 `exit 2` 并打印是哪一处。
     光靠 `heal` 挡不住 —— 备份本身可能就是脏的。宁可当场停，
     也别带着一处假改动跑完 207 项还绿着提交。
  3. **`.mutbak` 必须进 `.gitignore`。** 它躺在源码旁边，`git add -A` 会把它当新文件吃进去，
     而它装的是"改坏之前"的源码 —— 进仓库就是一份假的"源码备份"。
  另外：**别用 `Edit` 工具同时改同一个文件的两处** —— 两次编辑各自读一遍原文再写回，
  后写的会把先写的那处冲掉（本轮踩过：`buildPlan` 里 `const ps` 那句就这么没了，
  症状是页面运行时报 `ps is not defined`，而编辑工具两次都回"成功"）。
- **`e2e.js` 里读 `.dep` 一类列表时用 `data-slot`，别用数组下标。** 见上一节第 12 条。
- **测试 MIDI 的手写生成器极易造出非法文件**：一个事件必须是「delta-time + 事件」的完整单元。
  曾经把 `vlq(480)` 和后面第一组 `vlq(0)` 分开写，导致事件里出现两个 delta-time，
  解析器按 running status 一路错位。表现形式是「音符数量对但时间全歪」。
  所以生成的每个文件都要先用 `ref_parse.py` 验一遍结构。
- **解析器遇到损坏文件应该降级而不是崩**：读越界返回 0 并置 `truncated` 标记，界面上给出黄色提示。
  如果用裸 `DataView.getUint8()`，一个坏字段就会抛 `Offset is outside the bounds of the DataView`。
- **`SCAN` 不可靠**：浏览器端也是逐个 `PING 1~10`，每个约 0.6 秒，一次检测约 6 秒属正常。
  （这是**原厂固件**的历史现象；自研 `PIANO_GLOVE_2` 把舵机侧超时收到 20 ms，
  且在线检测改成轮转单槽 + 8 ms 超时，实机已稳定报 6 块。见设计笔记风险 5。）
- **模拟固件必须忠实实现固件的语义，否则这套测试就是自欺欺人**。踩过两次：
  - `MockFirmware.reset()` 顺手把 `onAsync` 清成了 `null` —— 那是 `Transport` 在构造时接上的
    唯一一根「异步出口」线。结果是 4C 测速 e2e 6 项 FAIL（`#rtResult` 永远不可见）。
  - 「重置向导」按钮顺手调了 `T.mock.reset(true)`（恢复出厂）→ 档位掉回 `SC09`（量程 1023），
    行程只剩真实的 1/4，模拟算出 **11.6 Hz** 而实机只有 **5.0 Hz**，**偏差 4 倍**。
    真机上按这个按钮，板子那边一个字节都不发 —— 所以模拟侧也不该发。
- **无头浏览器的 `rAF` 频率远低于 60 fps**（实测约 8 fps）。凡是要观察动画中间态的断言，
  都必须多次采样取极值，不能只读一次。
- **实机脚本不要用「静默 N 秒就收工」判断测速结束**。最初 `rate_test()` 写的是
  「静默 1.5 s 结束」，结果 6 根舵机同步卡住时被误判成「没反应」，
  实际板子还在跑。改成**只有连 `RATE_START` 都没见到时**才提前收工。
- **JS 里 `p += readVlq()` 是错的，必须拆成两步。** `+=` 先取 `p` 的**旧值**再求右边，
  而 `readVlq()` 内部已经把 `p` 推进了「长度字段自身占的字节数」，返回值只是长度值 ——
  结果 `p` 少前进 1~2 字节，每读一个 meta 就错位一点。
  现象极具迷惑性：扫出 `meta 0x00`、却扫不到本该有的 `0x2F`，而且**短文件错位后可能碰巧再对上**，
  长的才露馅。Python 版写成了两步所以是对的，两边不一致才把它暴露出来（这正是保持
  「同一件事有两个独立实现」的价值）。
- **同一时刻、同一个音高只能有一个 note-on。** 编配多声部时最容易犯：
  《革命练习曲》里左手琶音的音恰好落在右手和弦的音上（都是 Cm 的组成音），
  不去重的话文件标称 256 个音、解析出来只有 240 —— 差的那 16 个是撞车的。
  一个键按不了两次，DAW 和上位机都会把后一个 note-on 当重复触发合并掉。
  生成器里做了去重，断言里也比对了「解析音符数 == catalog 里标的音符数」。

### 写「串口桥」这一层时踩的坑

- **`open()` 里千万别 `reset_input_buffer()`。** 桥原来是「打开 → 睡 0.25s → reset → 读一坨
  当"上电主动上报"」，而 reset 恰好把板子上电自己吐的那行 `BOOT` 清掉了。
  自测里那条「上电上报必须作为 `pre` 还回来」的断言就是这么照出来的。
  正确做法：`open()` 之后**立刻**起读线程，什么都不会漏。
- **开串口会让 ESP32 复位**（CP2102 的 DTR/RTS 接着自动复位电路）。所以
  「先探测、再连接」= 复位两次，而且探测那一发 `INFO` 十有八九打在启动过程里，
  把真板子判成"不是它" —— 自动连接就成了随机事件。
  现在的做法：直接打开，然后 `_wait_info()` 耐心问 4 次（约 2.8 秒），答了就是它。
- **`/api/disconnect` 必须把自动重连停掉。** 一开始没停，结果「断开」按钮前脚按下去、
  后脚那个 1 秒一轮的重连循环又给连回来了，按钮等于没用（断言 `paused` 就是这么加的）。
- **「自动选推荐口」不能依赖调用方排序。** `autoconnect_once()` 原来直接用 `self.ports` 的顺序，
  上游哪天忘了 sort 就悄悄退化成"按枚举顺序碰运气"。现在它自己 `cands.sort(by -score)` ——
  这条是单测（`test_autoconnect_order`）逼出来的，它故意喂了一个乱序列表。
- **异步行必须"立刻发出去"，不能先攒着。** `fake_glove.py` 最初把回复 `append` 进一个列表、
  等 `handle()` 返回后统一发。`RATE_DONE` 是 0.45 秒后才 append 的，那时列表早发完并丢弃了 ——
  一个字都出不去。改成 `emit` 立刻发。
- **变异测试脚本要处理 CRLF。** 源码是 CRLF 而模式串照着 LF 手写，`includes()` 永远 false，
  脚本会误报「变异点找不到（源码变了？）」—— 于是三条变异里两条**根本没注入**，
  却看起来像是"源码变了"。而且还原要挂在 `process.on("exit")` 上，绝不能把变异留进工作区。
- **断言 `window.T` 是取不到的。** 页面里 `T` 是顶层 `const`，只在全局**词法**作用域里，
  没有挂到 `window`。得用 `typeof T !== "undefined"` 探。
- **查"正文里还有没有某字样"要用 `innerText`，不能用 `textContent`。**
  `textContent` 会把 `<script>` / `<style>` 里的文本也算进去，
  于是源码注释里那几处「模拟模式」让断言永远红。
- **判断元素可见性前要先切到那一页。** `#assignBody` 在 `#p-assign` 里，
  停在连接页时 `isVisible()` 对非活动页永远返回 false。
- **页面原来只会朝「自己的来源」找桥 —— 这是用户实际踩的坑。**
  原来 `detectBridge()` 用的是相对路径 `fetch("/api/status")`，于是：
  被别的本地服务器托管（内置浏览器预览、别的 dev server）时问到别人家、404；
  **直接双击 .html（`file://`）时更彻底 —— 相对路径被解析成 `file:///C:/api/status`**，
  控制台报 CORS 被拦。两种症状是同一句「没找到本地串口服务」，可桥明明在跑。
  更要命的是**自测从来没照过它**：第 8 节的桥测试一直用 `http://127.0.0.1:<桥端口>/`
  同源打开，等于把这条路径焊死在「正确用法」上。
  现在页面按候选清单朝绝对地址问（同源 → `127.0.0.1` / `localhost` 的 8123~8130），
  桥那边回 CORS 头 —— **两边都要改，只改一边没用**。
- **跨来源 POST 还要过预检。** 页面发的是 `Content-Type: application/json`，
  浏览器会先发 `OPTIONS`；`BaseHTTPRequestHandler` 默认没有 `do_OPTIONS`，
  回 501 就把整条请求掐了 —— 现象是「页面看着连上了，命令一条也到不了」。
  所以桥必须实现 `do_OPTIONS` 并回 `Access-Control-Allow-Headers: Content-Type`。
- **测跨来源时一定要用 `?bridge=` 把地址钉死，不能靠默认清单扫。**
  默认清单里有 `8123`，而用户自己的桥多半就开在那儿 —— 一旦扫到它，
  测试就会去连**真板子、真拧舵机**。测试永远不许碰真硬件。
- **`file://` 来源的 `Origin` 头是 `null`**，不是没有头。`_origin_ok()` 里
  `urlparse("null").hostname` 是 `None`，会被当成外站拒掉，所以得显式放行 `null`。
- **变异点要「只砍那一条路」，砍太粗会伪装成「没咬住」。**
  给「跨来源找桥」写变异时，第一版是把整个候选循环置空 —— 结果**同源也连不上了**：
  第 8 节前面几条先红、`T.send` 抛异常穿过整节、脚本在跑到目标断言之前就崩了，
  于是报「✗ 没红 ← 这条断言是假绿」。可它其实**是真绿的**，只是没被执行到。
  正确写法是只砍掉非本页来源的候选（`bridgeBases()` 里那几行 → `add("")`），
  同源照常可用。判据：**期望那条断言必须出现在实际 FAIL 列表里**，否则先怀疑
  「变异点太粗 + 套件中途崩了」，别急着改断言。
- **长套件里任何一次 `await` 抛异常都会穿过整节**，后面上百条断言一条都不跑。
  凡是「可能没连上就直接发」的调用（`T.send` 这种），一律包一层 try 让它**红而不崩** ——
  崩掉的套件会把真正的失败点埋在只剩三条的日志里。`mutate_play.js` 现在也会
  检测「e2e 有没有跑到结尾」，没跑到就提醒一句。
- **`node -e "require('./tests/mutate_play.js')"` 会当场把变异跑起来**（它是脚本不是模块，
  没有 `require.main === module` 守卫）。想核对它的 `find` 串能不能匹配源码，
  用 `fs.readFileSync` 自己读、自己 `includes`，**千万别 require 它**。
  本轮就这么误触发了一次，脚本被外层超时 SIGTERM 打断，源码留在改坏状态
  （靠 `.mutbak` 还原的）。
- **SIGTERM 会跳过 `finally`。** 变异脚本现在把还原同时挂在
  `SIGINT/SIGTERM/SIGHUP/SIGBREAK` 上；Windows 上未捕获的强杀仍挡不住，
  那种情况靠启动时的 `healLeftovers()` + `verifyClean()` 兜底。
